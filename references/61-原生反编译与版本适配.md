# 61 · 原生反编译与版本适配

> 适用：Windows x64 WH3 EXE / 原生 MOD DLL；案例输入为 WH3 9.0.4.0。
> 事实截止：2026-10-21（文档整理）；来源：2026-10-17 狐女小屋原生审计、模型根定向研究与适配器的历史方法摘要；证据边界见 §6。
> 边界：本册整理已存在的静态证据与隔离测试方法，没有新增游戏实测，也不宣称恢复 CA 或缺失的 MOD 原始源码。

## 1. 先定问题与输入身份

先查 `60` 的日志和故障层级。DB、Lua、布局能解释的行为先沿对应原文件追踪；原生门禁、旧地址、结构字段、调用约定或 DLL 内部行为才进入本册。将结果组织成机制伪源码时配合 `44`。

记录 EXE、DLL 的完整路径、大小、SHA256、PE machine/image base、游戏 FileVersion/build，以及载荷的来源 pack/脚本。从 `native_bin.lua` 取 DLL 时仅解析确定的 base64 数据块并解码，核对长度/身份；不要为提取字节执行 Lua 或加载未知 DLL。

把工作目录放项目 `_work/<本次分析>/`，保存输入指纹、PE 元数据、脚本、函数范围、原始指令、反编译正文和结论。使用者自行确认 Ghidra、兼容 JDK 和脚本解释器；依赖见 [工具清单与准备](../工具清单与准备.md)。PATH 未配置时使用自己确认的可执行文件路径，不能沿用作者安装状态。分析工程与日志不得进入发布源目录的资源树。

## 2. 两种分析规模

### 2.1 小 DLL：从导出与注册点进入

对小型业务 DLL 可做完整导入分析，再沿 Lua 导出注册、版本检查、安装/卸载 hook、状态输出与错误字符串定位目标。导出名、错误文案和注册字符串有助于定位，不能单凭字符串邻近推定函数语义。

优先还原实际执行的检查顺序与数据流。例如本例版本检查先比较文件大小，再计算 SHA256；两段 hash 常量虽交换存放，SSE 比较却正确对应输出半块。是否接受版本由实际比较指令决定，不按错误提示里的版本文字或常量连续显示顺序下结论。

### 2.2 大 EXE：定向函数导入

从 DLL 的已知调用、当前同类代码、字符串/字段与调用点筛选目标，先读 PE 节表和 `.pdata` 的函数范围；本例先取 17 段、后补到 26 段，不需要全量反编译整个游戏。

可在 Ghidra raw seed 工程中，把只读提取的函数块加载到各自 **preferred image base + RVA**，指定正确的 x64 language，再定向 disassemble / createFunction / decompile。保持原地址，保证 rel32/RIP 解码关系；缺失的代码、数据段或外部函数原型会限制反编译结论，按需补入。`.pdata` 是本例有效的范围线索，不能假定它列出全部叶函数、内联体或入口。

定向脚本和启动参数由使用者按目标 PE 与已安装 Ghidra 编写；示例 base `0x140000000` 仅适用该历史 EXE，不能硬编码成全部输入的基址。`-noanalysis` 是避免全局自动分析，后置脚本仍显式创建和反编译目标函数。重跑工程注意 `-import` 与 `-process` 区别，避免重复导入；Windows `-scriptPath` 的尾反斜线会影响引号，可用不以反斜线结尾的目录形式，例如 `.../.`，并核实实际传参。

**成功判据**：目标输出存在，所需函数的反编译完成，且含对应地址/机器码/指令与可复核结果。headless 退出 0、工程存在或日志写了导入成功，都不能单独证明目标已反编译。

## 3. 机器码与地址换算

| 项目 | 处理方式 |
|---|---|
| RVA / preferred VA / runtime VA | `preferred VA = PE ImageBase + RVA`；`runtime VA = 实时模块基址 + RVA`。ASLR 后不要用 preferred VA 访问进程 |
| 文件偏移 | 找覆盖该 RVA 的节，`PointerToRawData + (RVA - VirtualAddress)`；检查落在实际原始字节范围内。虚拟零填充没有对应磁盘字节 |
| RIP-relative | `指令末地址 + sign_extend(disp32)`，记录 opcode、指令长度和目标节；区分 LEA 取地址与 MOV 取值 |
| `E8 rel32` | `CALL 地址 + 5 + sign_extend(rel32)`；返回地址是下一条指令，不能把签名起点当返回点 |
| 立即数与指针算术 | 回指令字节核对；Ghidra 错误的指针类型会把 C 表达式中的加数按结构大小缩放 |
| 字节搜索 | 命中只是候选；进入真实函数范围后反汇编确认指令边界，再分析数据流 |

本例 Ghidra 的 `HMODULE` 类型推断将真实 `+0x1c6a30c` 显示为 C 表达式 `+0x71a8c3`；以 LEA 指令立即数为准。`48 83 E9 80` 是有符号 imm8 的 `SUB RCX,-0x80`，效果为加 `0x80`，不能读成减 128。

扫描 E8 只能覆盖该种直接 CALL；有限 RIP 指令模板扫描未命中，也不能断言没有 xref。磁盘全局槽的初值为 0，不证明运行时为空、地址失效或无法静态定位。

## 4. 从候选到可用解析规则

1. 在已确认的函数指令中选择语义稳定的上下文，通配 CALL/RIP 的版本相关位移；用于证明结构的字段偏移保持固定。
2. 在当前 PE 可执行节重扫，记录匹配数。必需规则要求唯一；0 次或多次时停止启用受影响功能并报告原因，不选“最近地址”。相同函数模板可经已确认的唯一调用者闭合，不能随意选一个副本。
3. 解码目标后验证所在节、地址范围、函数入口/范围、调用目标和关键后继指令，检查长度与算术溢出。
4. 用独立路径交叉核对对象根和用途。本例 cooking 与 units 两条路径解析到同一个根槽，并分别闭合到 validate/clear/apply 和 lookup_unit；槽地址不能当模型对象。
5. 分开验证函数 ABI、参数来源、返回值、结构偏移、调用者返回点和生命周期。签名唯一及前 32 字节一致，只证明那一段字节，不证明全部语义。
6. 规则保存为项目 manifest：输入 SHA、pattern/mask、匹配数、解码公式、期望关系和证据位置。游戏更新后按 `05` 重新解析与审查，不沿用旧地址增量或自动重写 expected bytes 来制造“通过”。

历史 DLL 审计中 15 条有效签名匹配，仍留下旧根和手动返回点依赖；把其余签名长度设为 0 不构成补证。版本大小/hash 门禁和地址/结构验证是不同层，不能只改版本常量就称为适配完成。用动态解析替换精确版本门禁时，应有可检查的定位与结构检查承接。

## 5. 适配落地与生命周期边界

此节用于实现适配器时的复核；单纯分析无需启动游戏或安装 hook。修改范围遵守当前任务授权，分析需求本身不包含部署或发布。

- **定位与运行时分开**：磁盘 EXE 用于稳定字节定位；运行对象用匹配身份的实时模块基址解析。主菜单、加载中、战役切换时根/子对象可为空，应区分暂不可用和签名错误。
- **跨档重新取对象**：模块是否还在、Lua 状态是否重建、hook 是否仍在以及模型是否换实例分别判断。不要跨存档缓存已解引用的模型指针。
- **只处理已确认归属的 hook**：入口以 E9/FF 开头或与磁盘不同，不能证明它属于本 MOD。恢复前需验证目标、跳转归属、保存的原字节和模块生命周期；遇到未知修改时保留现场、停止受影响安装并说明冲突。本例历史审计指出被审查的恢复逻辑尚有这一缺口，不能将它直接复制为通用恢复方案。
- **区分服务失败**：原生能力失败不应无条件中断无关 Lua 服务；依赖原生的制造/应用在执行端明确拒绝，不能仅让按钮失效。重试次数、时机和清理条件按实际失败类型设定，不无限重装 hook。
- **补丁与回滚单独验**：若维护自有 DLL 的适配，先固定基线身份、确认所有预期字节与修改范围，再验证失败回滚。不得把这一过程扩大为修改磁盘游戏 EXE，或声称可以还原未知第三方状态。

验收按证据分层：离线唯一性/解码 → 隔离进程中的边界与失败恢复 → 游戏中正常调用上下文的对象与结果 → 同进程读档/回主菜单重进 → 实际第三方冲突组合。单人验证不证明多人同步安全。`prepared` 只说明定位准备完成；业务日志、库存/费用/效果及存档行为仍需对应验证。

## 6. 公开版来源与版本范围

本册保留历史静态分析的结论摘要与可复用流程；原始审计文件、签名 manifest、DLL、游戏 EXE、Ghidra 工程和测试载荷不随包分发。它们不是读者执行本技能的前置文件；复现时应从自己的授权输入重新建立证据。

历史 EXE 身份：2026-10-17，WH3 9.0.4.0，232,531,920 字节，SHA256 `9bd58c63bd7fc5c9909b3d3d9b6b7a6ae4eac784369bf91a9e53c3e9f42be496`，preferred base `0x140000000`。此指纹仅绑定文中例子，不作当前版本白名单，也不证明读者版本兼容。

使用者每次分析应保存：输入指纹与 PE 元数据、函数范围、原始指令和反编译结果、pattern/mask 与匹配数、解码关系、测试输入与观察、未知项。缺少实际证据时明确标为推断或待验，不能把作者历史结果升级成自己的实测。

Ghidra 的安装与 JDK 要求按 [官方项目说明](https://github.com/NationalSecurityAgency/ghidra) 和所选发行包文档核实；本包不固定作者机器上的软件版本或安装位置。

运行时样本、可读范围、调用图与字段数据流见 [62](62-运行时样本与内存研究.md)，Lua/UI 状态证据先按 [63](63-MCP证据与日志整理.md) 核实。

- [ ] 输入身份、地址坐标系、PE 映射和分析范围明确；所需反编译实际完成。
- [ ] 关键 C 表达式已回机器指令核对；字节候选、语义命名和已闭合数据流有区别。
- [ ] 所需签名唯一，目标解码、对象根交叉验证、字段偏移和 ABI 有依据；缺口没有用跳过校验掩盖。
- [ ] 零/多匹配、未知入口改写、空模型、模块重入、失败恢复均有处理或明确待验项。
- [ ] 测试记录注明输入和覆盖层级；静态成功、离线模拟及打包回读均没有冒充游戏兼容完成。
