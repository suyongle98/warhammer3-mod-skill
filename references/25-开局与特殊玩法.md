## 1. 自定义开局军队（脚本）

**原理**：脚本在首次 tick 时把目标派系开局将领的 `units` 字段替换成你的兵种列表。改的是"实际部队"，**选人界面不变**。

### 1.1 脚本目录

| 生效范围 | 目录（相对 pack 根） |
|---|---|
| 仅超凡帝国 | `script\campaign\wh3_main_combi\mod\` |
| 仅混沌魔域 | `script\campaign\wh3_main_chaos\mod\` |
| 两战役都生效 | `script\campaign\mod\` |

- **依据**：`游戏原文件\db\campaigns_tables\data__.tsv` 的 `script_path` 列为 `wh3_main_combi` / `wh3_main_chaos` / `wh3_main_prologue`（`campaign_name` 同名列）。
- **验收**：只开超凡帝国一档，脚本日志有输出；换混沌魔域再开一档，输出仍在。

> ⚠️ 坑：沿用 WH2 的 `main_warhammer` / `wh2_main_great_vortex` → 脚本静默不执行（教程 18 评论区实测结论）。

### 1.2 函数名两处必须一致

教程 18 第二步：脚本内**注册处的函数名**与**定义处的函数名**必须完全相同（原文"上下蓝框的文字必须相同"）。示例把 `edit_starting_army` 改为 `test_start_army`，两处同改。

- **怎么做**：注册段与定义段用同一个字符串，且带 MOD 前缀（如 `my_mod_edit_starting_army`）。
- **验收**：改名后 `luac5.1.exe -p` 通过，且进游戏脚本有输出；只改一处 → 无输出且无报错。

> ⚠️ 坑：只改定义处不改注册处 → 回调指向不存在的函数，脚本"看起来在跑但什么都不做"。

### 1.3 四个字段

| 字段 | 取码表 |
|---|---|
| `faction` | `factions_tables.key` |
| `subtype` | `agent_subtypes_tables.key` |
| `forename` | `names` 表键 + `names_name_` 前缀；可按中文名在 `localisation__.loc.tsv` 反查 |
| `units` | 单位代码，逗号分隔（与 `cm:create_force` 的 unit list 同域） |

- **取代码方法**：一律查历史案例原文件——`<VANILLA>\db\<表>_tables\data__.tsv`，不要沿用教程的 WH2 码（`wh2_main_hef_eataine` / `wh2_main_hef_tyrion` / `names_name_2147360906`）。
- **验收**：新档开局该派系将领带的兵与你填的列表逐项一致；将领子分类正确。

> ⚠️ 坑：`units` 里混入只存在于 `land_units_tables` 的单位码 → 该单位不出现在开局部队里（WH3 两表 key 有 49 个只在 `land_units` 中的差异）。

### 1.4 选人界面不建议动

修改选人界面需要改 `startpos.esf`，MOD 兼容性代价大，教程 18 明确"一般不建议去改"。**做法**：接受界面与实机不一致，功能以实机为准。

## 2. 召唤（脚本，六种触发场景）

| # | 场景 | 触发点 | 备注 |
|---|---|---|---|
| 1 | 开局进招募池 | 首次 tick（`_new` 系列） | 仅新游戏 |
| 2 | 直接入招募池 | 无条件/条件判断 | **兼容旧存档**；配幂等键防重复 |
| 3 | 建筑完成入池 | `BuildingCompleted` 事件 | 事件监听必须在 `cm:add_first_tick_callback` 内注册 |

| 6 | 占领某地召唤 | `RegionFactionChangeEvent` | 地区码查 `regions_tables` |

### 2.1 两个 API（签名已在历史案例 lib 核对）

```lua
-- 入招募池（11 参数；第 10 个参数 = 是否不朽）
cm:spawn_character_to_pool(faction_key, forename, surname, clan_name, family_name,
                           age, is_male, agent_type, agent_subtype, immortal, art_set)

-- 直接放到地图坐标（15 参数；unit_list 可为空串）
cm:create_force_with_general(faction_key, unit_list, region_key, x, y,
                             agent_type, agent_subtype, forename, clan_name, family_name,
                             other_name, make_faction_leader, success_callback,
                             force_diplomatic_discovery, no_background_trait)

-- 只放事务官（6 参数）
cm:create_agent(faction_key, agent_key, subtype_key, x, y, disable_auto_select)
```

- 参数含义依据：`lib_campaign_manager.lua` L6635-6790（`create_force_with_general`）、L6928-7005（`create_agent`）；`spawn_character_to_pool` 为引擎函数，参数名由 WH3 原版脚本用法反推。
- `create_force_with_general` 的 `region_key` **必须真实存在**（lib 会校验，否则 `script_error`）。

### 2.2 「无专属名字与不朽」——WH3 已可覆盖

- 教程 22（WH2）结论：脚本召唤的领主**拿不到专属名字与不朽**，只能用 Effect 放到特性里补。
- **WH3 实测更正**：`spawn_character_to_pool` 第 10 参数可传 `true` 给不朽。原版用法：`wh3_main_chaos\wh3_boris.lua` L161、`wh3_dlc27_asur_domination.lua` L618 都传 `true`。专属名字仍取决于 `forename`/`surname` 是否指向传奇姓名键。
- **验收**：召唤出的角色详情面板显示"不朽"；死亡后进入康复而非永久死亡。

> ⚠️ 坑：照抄教程 22 说"脚本召唤必不不朽" → 白写一套 Effect 兜底；先试第 10 参数。

### 2.3 取坐标方法 【待核对】

教程 22（WH2）流程：订阅坐标显示 MOD → 开新档 → 移动领主到目标点 → 结束回合 → 退出游戏 → 游戏目录生成 `coordinates*.txt` → 读坐标。

- **WH3 未验证项**：① 是否仍生成 `coordinates*.txt`；② 是否各战役坐标不同（WH2 凡世与大漩涡不同，需分别写脚本）；③ 文件落盘位置。
- **核对法**：按上述流程跑一档，在 WH3 安装目录（含 `Warhammer3.exe` 的目录）搜 `coordinates*.txt`；有则记录，无则改用定位 API。
- **替代做法（WH3 原版验证，62 处用法）**：`cm:find_valid_spawn_location_for_character_from_settlement(faction_key, region_key, on_sea, same_region, prefered_distance)` 返回 `x, y`。范例：`游戏原文件\script\campaign\wh3_main_chaos\wh3_boris.lua` L179。

### 2.4 幂等

所有"只做一次"的召唤都要用 `cm:get_saved_value` / `cm:set_saved_value` 加键保护，否则读档重复召唤。做法见 `40-Lua战役脚本.md` §7。

- **验收**：触发 → 存档 → 读档，角色不重复出现。

## 3. 开局采购两难（dilemma + campaign payload）

**用途**：开局弹一个两难窗，让玩家花国库金币买单位 / 买加成 —— 比"直接白送"更有代入感，且不依赖存档改写。
（实测案例：`su_tiandeng` 天灯/天舟采购、`su_heimache` 黑马车采购 + 容量 +1。）

### 3.1 六张表的分工

| # | 表（版本） | 一行写什么 |
|---|---|---|
| 1 | `dilemmas_tables`（3） | 两难本体：`key` / `localised_description` / `localised_title` / `ui_image`（`faction`）/ `event_category`（`Event`）/ `is_large_dilemma`（`false`） |
| 2 | `cdir_events_dilemma_choice_details_tables`（4） | 每个选项一行：`choice_key`（`FIRST` / `SECOND` / …）+ `dilemma_key` |
| 3 | `cdir_events_dilemma_option_junctions_tables`（1） | `id` + `dilemma_key` + `option_key`（`GEN_TARGET_MODEL`）+ `target`（`default`） |
| 4 | `cdir_events_dilemma_payloads_tables`（0） | 每个选项的**每条**效果一行；`payload_key` 见 §3.2 |
| 5 | `campaign_payloads_tables`（0） | 只声明载荷 key（1 列） |
| 6 | `campaign_payload_unit_components_tables`（1） | 载荷内容：`add_unit` + `unit`（→ `main_units_tables`）+ `amount` + `xp` + `ignore_unit_cap` |

### 3.2 常用 `payload_key`（第 4 张表 `value` 列的语法）

| payload_key | value 写法 | 作用 |
|---|---|---|
| `CAMPAIGN_PAYLOAD_RECORD` | `PAYLOAD[<载荷key>];MILITARY_FORCE;` | 执行第 5/6 张表定义的载荷（把单位发到目标军队） |
| `TREASURY` | `AMOUNT[-1100]` | 国库增减（采购用负数） |
| `FACTION_POOLED_RESOURCE_TRANSACTION` | `RESOURCE[tmb_canopic_jars];FACTOR[canopic_jars_events_negative];AMOUNT[-100];CONTEXT[absolute];REQUIRED` | 消耗100脏器罐；`REQUIRED`要求能支付才允许选择。资源与因子绑定必须查原版同类行 |
| `EFFECT_BUNDLE` | `KEY[<bundle_key>];DURATION[0];GLOBAL` | 给派系挂效果组。**`DURATION[0]` = 常驻**（不给回合数）；"买了才给容量 +1"就走这条 |
| `TEXT_DISPLAY` / `ADD_ANCILLARY` / `GIVE_TRAIT` / `SPAWN_AGENT` / `LOYALTY` / `DIPLOMATIC_STANDING` … | 见 15 册 | 原版 20 余种，用前先 grep 原版同 `payload_key` 的写法 |

### 3.3 触发脚本

```lua
local triggered = cm:trigger_dilemma_with_targets(
    faction:command_queue_index(),   -- 玩家派系
    "你的_dilemma_key",
    0, 0, 0,
    force:command_queue_index(),     -- 目标军队（一般取领袖所在部队）
    0, 0
)
```

- **先决定旧档行为**：只对新战役发放时，用 `cm:add_first_tick_callback_new`保存按派系区分的资格键 `eligible`；每局 `cm:add_first_tick_callback`负责延迟触发与恢复重试，只处理有资格且未 `issued`的派系。需要主动补发旧档时，才采用没有新档资格门槛的迁移逻辑。仅有防重复键不能排除未安装过MOD的旧档。
- **返回值与防重复**：上例调用的是 `cm`包装函数；9.0.3 `lib_campaign_manager.lua`返回布尔值。若用 `pcall`，同时检查 `ok`及 `triggered==true`，`false`或异常均不写 `issued`。单机函数默认通过 intervention排队，返回 `true`表示请求已排队，不能据此断言已弹窗或发奖；需要记录实际发出时用第9参数 `on_trigger_callback`。第10参数 `force_dilemma_immediately`按时序需求选，默认不强制。
- **时序与重试**：每局回调中用 `cm:callback(..., 1.0)`等待模型与UI就绪；如需开局失败重试，可在前3回合注册 `FactionTurnStart`，调用入口和监听条件都检查回合、资格及 `issued`。按派系区分标记，监听只匹配相应玩家；多人环境另行实测。
- 派系判定用 `faction:subculture() == "wh_main_sc_..."`（键查 `cultures_subcultures_tables`）—— 写死派系 key 会只覆盖一个传奇领主；
- 发放前查满编：`force:unit_list():num_items() >= 20` 就跳过（否则单位会被丢弃）；
- 参考：`已完成mod/su_tiandeng/script/campaign/mod/su_tiandeng_purchase.lua`用于DB事件结构；`su_gmzc/su_gmzc/script/campaign/mod/su_gmzc_purchase.lua`展示新档资格、按派系防重复、失败重试与两选项采购，47项模拟断言与成品回读已通过，尚未游戏实测。

### 3.4 硬坑

- **`cdir_events_dilemma_payloads_tables.id` 是 I32，不是 I64**（原版最大已用到 2,147,401,755）—— MOD 号段必须 **< 2,147,483,647**，取号后先 grep 原版确认没被占用。`campaign_payload_unit_components_tables.id`、`cdir_events_dilemma_option_junctions_tables.id` 同理。
- **第 6 张表的列顺序是 `… amount / xp / ignore_unit_cap`**（2026-09-25 游戏更新后实测）。照抄旧 mod 的 `… amount / ignore_unit_cap / xp` 会**静默列错位**——本次实测两列的值恰好是 `false` / `0`（数值等价）才没暴雷。
- `add_unit`的 `ignore_unit_cap`：`true`绕过本次发放的单位容量检查，**不会增加永久招募容量**。直接给开局单位或同选项先加容量后发单位时，按需求使用 `true`；需要遵守容量时保留 `false`并验收满容量分支。常规招募容量另由12册§8.1的链路管理。
- **费用与放弃**：金币、池资源与单位奖励同放采购选项的原生载荷，Lua只触发事件，不再重复扣费或发单位。脏器罐 `REQUIRED`范例来自原版 `wh2_dlc09_tmb_dilemma_eternal_servitude`；没有费用和奖励的选项可仅登记choice及本地化，不添加payload。新档是否有足够资源另查，不以赠送资源绕过购买条件。
- 发放的 `unit` 必须取自 **`main_units_tables`**（不是 `land_units_tables`），否则静默失败。
- 选项 loc 键名固定为 `cdir_events_dilemma_choice_details_localised_choice_label_<dilemma_key><choice_key>` 与 `..._title_<dilemma_key><choice_key>`；两难本体是 `dilemmas_localised_title_<key>` / `dilemmas_localised_description_<key>`。少一个就显示键名原文。
- 打包前用 `modcheck` 跑一遍（表头/列数/loc 键名/引用闭合全查，见 03 册）。

## 4. 全局难度修改

**表**：`campaign_difficulty_handicap_effects_tables`（WH3 列：`campaign_difficulty_handicap` / `human` / `effect` / `optional_campaign_key` / `effect_scope` / `effect_value`）。

### 4.1 三要素

| 要素 | 说明 |
|---|---|
| `effect` | 效果代码，查 `effects_tables` + `localisation__.loc.tsv` 反查中文 |
| `effect_scope` | 作用对象，查 `campaign_effect_scopes_tables`（`key` / `location` / `ownership` / `source` / `target` / `territory`） |
| `effect_value` | 数值，正负按效果定义 |

### 4.2 常用 Scope（WH3 实测出现在该表）

| Scope | 作用对象 |
|---|---|
| `faction_to_faction_own` | 势力至势力（派系级） |
| `faction_to_character_own` | 势力至角色（只影响领主/英雄单位） |
| `faction_to_force_own` | 势力至军队（全军所有单位） |
| `faction_to_province_own` | 势力至行省 |

- 同表里还有 `_unseen` 变体（不显示在 UI 提示里）与 `_alt_text` / `_factionwide_armytext` 变体；**照抄原版同类行的后缀**，不要自己拼。
- **怎么做**：改 `effect_scope` 就改变了"谁吃到这个加成"——同一个 `effect` 配 `faction_to_character_own` 只给英雄，配 `faction_to_force_own` 全军生效。
- **验收**：进游戏开对应难度，鼠标悬停难度提示或看角色/部队面板数值变化与设定一致。

> ⚠️ 坑：以为 `faction_to_character_own` 会给全军队 → 只有角色单位吃到，普通部队无变化。

### 4.3 难度档位映射

**WH2 教程 04 的值（不得直接采信，WH3 需重核）**：

| 难度 | 玩家 `campaign_difficulty_handicap` | AI `campaign_difficulty_handicap` | `human` |
|---|---|---|---|
| 简单 | 1 | −1 | 玩家勾 / AI 不勾 |
| 普通 | 0 | 0 | 同上 |
| 困难 | −1 | 1 | 同上 |
| 极难 | −2 | 2 | 同上 |
| 传奇 | −3 | 3 | 同上 |

- **WH3 实测**：`campaign_difficulty_handicap` 取值集合为 {−3,−2,−1,0,1,2,3}，`human` 为 true/false，共 322 行。
- **⭐ 难度名 ↔ 数字（已确认，来源 = RPFM schema 的字段说明，不是猜的）**：

  | 难度 | AI 行 `human=false` | 玩家行 `human=true` |
  |---|---|---|
  | 容易 | −1 | 1 |
  | 普通 | 0 | 0 |
  | 困难 | 1 | −1 |
  | 极难 | 2 | −2 |
  | 传奇 | 3 | −3 |

  即：AI 侧难度越高数值越大；玩家侧**符号相反**（玩家难度越高，加成越少／惩罚越大）。
- **核对法**：`Get-Content "<VANILLA>\db\campaign_difficulty_handicap_effects_tables\data__.tsv" | Select-Object -Skip 2 | ForEach-Object { ($_ -split "`t")[0..1] -join "," } | Group-Object` 列出全部档位组合。
- **`optional_campaign_key`**：WH3 322 行中 311 行留空，仅 6/4/1 行填 `wh3_main_chaos` / `wh3_main_combi` / `wh3_main_prologue` → **留空 = 全战役生效**。
- **⭐ 引擎唯一键是四元组**：`handicap + human + effect + optional_campaign_key`。
  证据：原版 `human=true` 的 `wh_main_effect_agent_field_line_of_sight_mod` 在 `wh3_main_chaos` / `wh3_main_combi` = 120、`wh3_main_prologue` = 40 —— 值不同却共用同一三元组，说明 campaign 参与唯一性，多行**并存累加**。
  **后果**：给某 effect 写"通用行（campaign 留空）"时，原版的"战役限定行"**不会失效**，两者会叠加 → 必须**显式把原版战役限定行覆盖为 0** 来中和。
- **验收**：改完后逐档进游戏确认生效范围，不要只看一档。

> ⚠️ 坑：照抄教程 04 的 30+ 条 `wh_main_effect_*` 清单（作者自注"守望与大肚 DLC 前整理"）→ WH3 里部分已失效或数值语义不同。**先在历史案例 `effects_tables` + loc 里检索确认该 effect 存在**。
