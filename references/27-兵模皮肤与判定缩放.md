## 1. 兵模与皮肤（教程 06）
### 1.1 层级
`dds`（贴图）→ `rigid_model_v2`（部件）→ `VariantMeshDefinition`（完整模型）→ `variants_tables.variant_filename` → `unit_variants_tables.variant`。
### 1.2 `variants_tables`（WH3 实测 8 列）
| 列 | 含义 | 要点 |
|---|---|---|
| `variant_name` | 主键 | 被 `unit_variants.variant` 引用 |
| `tech_folder` | 部分坐骑用 | 一般留空 |
| `variant_filename` | 兵模文件 | 指向 pack 内 VariantMeshDefinition |
| `low_poly_filename` / `super_low_poly_filename` | 低模 | 一般留空 |
| `mount_scale` | **只缩放坐骑** | 教程：暴龙 1.4→4 |
| `scale` | 缩放骑乘者/本体 | 英雄常用 1.15~1.2 |
| `scale_variation` | 队内大小差异 | 原版 0.05，单体填 0 |
### 1.3 改部件：槽与闭合标签
- `<SLOT name="...">` 下可指向 `VariantMeshDefinition` / `rigid_model_v2` / `wsmodel`；槽名可自取（`cape`/`quiver`/`beard`）。
- 披风、箭袋和武器都要核对蒙皮、骨骼或挂点；静态挂件与蒙皮部件不能混为一谈。
- > ⚠️ 坑：删掉 `</Slot>` 闭合标签 → 该部件不显示。
### 1.4 骨骼决定能否互换
- 同骨骼也要核对蒙皮和挂点；跨骨骼直接替换可能错乱，需要另做映射、重定向或重新蒙皮后验证。
- **WH3 骨骼实测取值**：`battle_animations_table_tables.skeleton` = `humanoid01` / `humanoid01b` / `humanoid01c` / `humanoid01d` / `humanoid01e` / `humanoid02` / `humanoid03` / `humanoid05` / `humanoid07` / `humanoid13` / `humanoid17` / `horse01` 等。动画 key 中仍可出现 `hu1`/`hu1d`；缩写不能直接确定骨骼或游戏代数，以 `skeleton` 与资源为准。
- 核对：`Select-String -LiteralPath '<VANILLA>\db\battle_animations_table_tables\data__.tsv' -Pattern '^hu1_emp'` → 看该行 `skeleton` 列。
- 验收：换完部件进战斗，模型正常无撕裂。
### 1.5 换武器：只换路径，不动槽格式
- 槽格式决定持械动作判定。只替换槽内模型路径；武器类型要与动作匹配（双手矛动作别塞剑）。
- > ⚠️ 坑：整段覆盖武器槽格式 → 武器消失、错位。
### 1.6 贴图 dds
- 一组通常 5 张：`diffuse`（颜色）/ `specular`（金属色）/ `gloss_map` / `mask` / `normal`；一般只改 `diffuse` + `specular`。
- 导出格式、Alpha 与 Mip 以该材质的可信原始 DDS 为准，不统一强转 BC1。用 `scripts/dds-inspect.js` 对拍头和 SHA，再解码检查像素；分类、恢复与批次验收见 `33-DDS贴图检查与恢复.md`。
- > ⚠️ 坑：格式不对 → 颜色错误或边缘毛边。
### 1.7 `rigid_model_v2` 换贴图路径
- 每个 Lod 都要改，且各 Lod 可能引用不同 dds；改完**必须重命名**，否则覆盖原版素材。
- 用兼容的 RPFM 模型编辑器逐 Lod 修改贴图引用，保存后核对实际路径；程序版本、位置与支持范围按使用者环境确认。
- 【待核对】教程的 pack 名（`variants.pack` / `variants_2.pack` / `variants_dds2.pack` / `warmachines.pack` 等）是 WH2 分类。核对：RPFM 打开 WH3 的 `data.pack` 等，按 `variantmesh\wh_variantmodels\<骨骼>\` 路径搜。
- 验收：新模型贴图生效，原版单位外观不变。

### 1.8 缩放模型 ≠ 缩放判定体（改大小必查）
- **`scale` / `mount_scale` 只改渲染模型，不改任何战斗判定**。被远程打中、单位互相推挤用的"底盘"来自 `battle_entities_tables`，与模型大小是**两套独立数据**。
- 只缩模型不缩 `radius` → 判定圈比看得见的模型大，**子弹打在模型外的空处也算命中**。
- 判定体字段（`battle_entities_tables`，58 列）与"缩模型时要不要跟着改"：

| 字段 | 作用 | 缩模型时 |
|---|---|---|
| `radius` | 碰撞圆半径（米）＝"底盘"：实体推挤 + 远程命中判定的基准 | **按同一比例改** |
| `shape` / `radii_ratio` | 判定形状（`circle`，或矩形的宽高比） | 一般不动 |
| `projectile_intersection_radius_ratio` | 远程判定半径系数（与 `radius` 相乘） | 一般不动，随 `radius` 自动缩【待核对：与 `radius` 的确切算式未做游戏内逐项实测】 |
| `height` | 垂直判定范围（投射物在高度方向能否相交） | **看需求**：缩了会让高抛弹道更难命中，属额外加强【待核对】 |
| `mass` | 冲撞 / 击退质量 | 不影响命中判定 |
| `size` | 体型等级（枚举 `very_small`…`very_large`，`medium` 及以上算大型） | 不能按比例缩，只能选现有枚举值 |
- **改 `radius` 前先确认 entity 是否专属**：同一 key 可能被多个单位共用（`land_units.man_entity`、`mounts_tables.entity`、`battle_personalities.battle_entity`、`battlefield_engines.battle_entity`、`land_unit_articulated_vehicles.articulated_entity`）。在 `游戏原文件\db` 全局搜该 key，**只被一个兵种/mount 引用**才可直接改，否则会波及其他单位。
- **"总被弹面积"另有两条线**：`land_units.num_mounts` = **坐骑模型个数**（天灯/天舟 = 1；罗盘战车 = 4 头牛、尸车 = 4 个僵尸、战鼓 = 2 头牛），改大 = 战场上多出判定体；`main_units.num_men` = 实体数；`unit_spacings_tables` 决定这些判定体彼此的间距。三者共同决定总被弹面积，改一个要连带看另外两个。
- **实测案例（2026-09-13，`su_tiandeng` 天灯）**：`variants_tables.wh3_main_cth_veh_sky_lantern.mount_scale` 1.0 → 0.7（灯笼外观缩到 70%），但 `battle_entities.wh3_main_cth_flying_sky_lantern.radius` 仍是原版 **3.1** → 判定圆直径仍 6.2 米（×0.9 系数后约 5.6 米），比 70% 的模型大约 1.4 倍；把 `radius` 同步改成 **2.2** 后才对齐。已核对：该 entity 只被 `mounts_tables.wh3_main_cth_mnt_sky_lantern` 引用，改动不外溢。
- 验收：进战斗从侧后方观察，投射物命中的边缘应与可见模型轮廓基本重合，不出现"明显打空却掉血"。
