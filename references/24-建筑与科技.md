## 1. 加新建筑：13 张表清单与顺序

按此顺序建，前一张的 key 是后一张的外键，跳序会留下悬空引用。

| # | 表 | 做什么 |
|---|---|---|
| 1 | `building_superchains_tables` | 注册高级序列 key |
| 2 | `building_chains_tables` | 注册序列，填 `building_superchain` |
| 3 | `building_chain_availability_set_ids_tables` | 需要新可用性集时才建 |
| 4 | `building_chain_availabilities_tables` | 集 → 文化/子文化/派系/战役 |
| 5 | `building_chain_availability_sets_tables` | 序列 → 可用性集（多对多） |
| 6 | `building_culture_variants_tables` | 注册建筑等级 key ＋ 图标/文本/文化变体 |
| 7 | `building_levels_tables` | 等级挂进序列，填费用/等级要求 |
| 8 | `building_instances_tables` | 同城可存在量 |
| 9 | `building_level_required_buildings_tables` | 前置建筑 |
| 10 | `building_upgrades_junction_tables` | 升级关系 |
| 11 | `building_set_to_building_junctions_tables` | 归入建筑组（影响 Effect 加成） |
| 12 | `building_effects_junction_tables` | 建筑加成 |
| 13 | `building_level_armed_citizenry_junctions_tables` | 驻军 |

**建筑组本身**（可选，第 11 步之前）：`building_sets_tables` = `key` / `icon` / `sort_order` / `show_in_ui` / `audio_switch` / `colour_hex`（六位十六进制，不是 WH2 的 Color R/G/B 三列）。

- **怎么做**：每一步都先复制一条原版同类行改值，不要空表手写。
- **验收**：新建 key 能被下游表选中、无 `Invalid reference`；`building_culture_variants_tables.building` 与 `building_levels_tables.level_name` **必须完全一致**。

> ⚠️ 坑：`building_culture_variants_tables` 里注册 `xxx_1`、`building_levels_tables` 里写 `xxx1` → 建筑不显示、图标为空，且无报错。

## 2. 序列与高级序列（superchain / chain）

- 一个**序列（chain）**＝一个建筑及其各级升级；一个**高级序列（superchain）**＝多条同类序列的集合，是把序列接到城市槽位模板的唯一通道。
- `building_chains_tables` 常用列：`key` / `chain_category` / `building_superchain` / `optional_sort_order` / `can_be_dismantled` / `is_foreign_slot_chain`；`tech_category_tab`、`tech_category_position`、`in_encyclopedia`、`optional_tier_icon`、`optional_required_horde_commander` 原版基本留空。
- **验收**：`building_chains_tables.building_superchain` 的值能在 `building_superchains_tables.key` 里查到。

> ⚠️ 坑：只注册 chain 不填 `building_superchain` → 建筑永远进不了任何城市槽位，游戏里根本看不到。

## 3. 可用性（文化 / 子文化 / 派系 / 战役）

链路是：`building_chain_availability_sets_tables`（chain ↔ set）→ `building_chain_availabilities_tables`（set → culture / sub_culture / faction / campaign）。

| 想限定 | 填哪一列 |
|---|---|
| 整个文化（如全人类） | `culture` |
| 具体子文化（如诺斯卡） | `sub_culture` |
| 单一派系（如瑞克领） | `faction` |
| 限定某战役 | `campaign` |

- 文化 ≠ 子文化：混沌与诺斯卡的 `culture` 同属混沌，但 `sub_culture` 不同；帝国/基斯里夫同理。取值查 `cultures_tables.key` 与 `cultures_subcultures_tables.subculture`。
- **两战役各一行**：教程 12 要求为同一 `set_id` 写两行、分别填 `wh3_main_chaos` 与 `wh3_main_combi`（`id` 不能重复）。**WH3 实测例外**：作者环境 `building_chain_availabilities_tables` 共 44 行，39 行 `campaign` 留空、5 行填 `wh3_main_prologue`；现役种族集（`wh3_main_bas_ksl` / `wh3_main_bas_cth` 等）**均为留空**。即 **`campaign` 留空 = 全战役生效**。**【待核对】**：留空是否在超凡帝国/魔域都生效需实机两战役各开一档确认（核对法：查 `游戏原文件\db\building_chain_availabilities_tables\data__.tsv` 第 6 列取值分布）。
- **验收**：目标派系新档能在建筑栏看到该序列；非目标派系看不到。

> ⚠️ 坑：把文化代码填进 `sub_culture`（或反之）→ 建筑在所有派系里都不出现，且日志无提示。

## 4. 文化变体与 `disables`（反选用法）

`building_culture_variants_tables` 一行 = 某建筑等级在某文化/子文化/派系下的外观与文本。

- **正向**：`building` = `xxx_1`，`culture` 留空 → 所有文化通用；填 `culture` → 仅该文化。
- **反选**：同一 `building` 再加一行，只填 `faction`（或 `sub_culture`），并勾选 `disables` → 通用建筑对该派系不可用。原版共 115 行 `disables=true`，就是这种用法。
- `icon` 只写档名（如 `tmb_pyramid_of_king_phar`），文件放 `ui\buildings\icons\`。
- `short_description` 填文本 key，`display_tooltip` 固定勾选，`description` 原版统一 `wh_main_PLACEHOLDER`，`building_frame_override` 仅 13 行用到（一般留空）。
- **验收**：同一建筑在不同派系下图标/名称不同；被 `disables` 的派系建筑栏里确实没有它。

> ⚠️ 坑：以为 `disables` 是"删除这一行" → 它是**排除标记**；不填 `faction`/`sub_culture` 就勾 `disables`，等于把该建筑对所有人生效的那一行也废掉。

## 5. `building_levels_tables` 关键列

| 列 | 含义 / 填法 |
|---|---|
| `level_name` | 建筑等级 key，与 `building_culture_variants_tables.building` 一致 |
| `chain` | 所属序列 |
| `level` | 等级序号，从 0 或 1 起（同序列内连续） |
| `create_time` / `create_cost` / `upkeep_cost` | 建造回合 / 造价 / 维持费（一般 0） |
| `development_point_cost` | 人口/发展点需求。WH3 原版 739 行非 0，**不是**可以随便留空的列 |
| `primary_slot_building_building_level_requirement` | 主城等级门槛（T 几能建）。WH3 实测取值 0–5 |
| `food_cost` | **WH3 全表 5259 行全为 0**：教程 12 的"木精灵琥珀"用法在 WH3 已不用；派系资源消耗走 `resource_cost` |
| `building_instance_key` | → `building_instances_tables.key` |
| `can_be_damaged` | 可被摧毁；WH3 有 443 行 `false`（废墟类） |
| `visible_in_ui` | 勾选 |
| `resource_cost` | 派系资源消耗（如古墓脏器罐） |
| `can_convert` / `only_in_capital` / `faction_unique` / `health_override` / `should_show_building_level_in_ui_for_technology` | 按原版同类行照抄 |

- **验收**：`level` 在同 `chain` 内不重复不断档；`primary_slot_building_building_level_requirement` ≤ 城市序列最高等级。

> ⚠️ 坑：照抄教程 12 把 `food_cost` 当木精灵琥珀用 → WH3 全表为 0，填了也不生效，应改用 `resource_cost`。

## 6. 同城存在量 / 前置 / 升级 / 建筑组

- **同城存在量**：`building_instances_tables`（`key` / `num_instances`）。绝大多数 1；绿皮粪坑类可 >1。`building_levels_tables.building_instance_key` 指向它。
- **前置建筑**：`building_level_required_buildings_tables`（`building_level` / `required`），两列都写建筑等级 key。原版仅少数派系用到。
- **升级**：`building_upgrades_junction_tables`（`from` / `to`）。
- **建筑组**：`building_set_to_building_junctions_tables` 的 `building_chain` 与 `building_level` **择一填**；填 `building_level` 时**每一级都要填一行**。建筑组影响 `effect_bonus_value_building_set_junctions_tables` 一类加成。
- **验收**：把鼠标悬停到建筑上，加成数值与 `building_effects_junction_tables` 一致；同城建两个超出 `num_instances` 的会被拒绝。

> ⚠️ 坑：`building_set_to_building_junctions_tables` 只填了 `_1` 那一级 → 升到 `_2` 后脱离建筑组，加成消失。

## 7. Effect 与驻军

**建筑效果** `building_effects_junction_tables`：

| 列 | 说明 |
|---|---|
| `building` | 建筑等级 key（不是序列 key） |
| `effect` | → `effects_tables.effect` |
| `context_requirement` | **WH3 新增列**，一般留空 |
| `effect_scope` | 常用 `region_to_region_own`、`province_to_region_own`、`building_to_building_own`、`this_building`、`building_to_faction_own` |
| `value` / `value_damaged` / `value_ruined` | 正常 / 建筑受损 / 建筑被毁时的值 |

> ⚠️ 坑：`value_damaged` / `value_ruined` 留空或与 `value` 相同 → 建筑受损/被毁后加成不降，等于白送永久 buff。废墟建筑应让两者为 0。

**驻军**（三表）：`building_level_armed_citizenry_junctions_tables`（`id` / `building_level` / `unit_group`）→ `armed_citizenry_unit_groups_tables`（只有 `unit_group` 一列，注册组）→ `armed_citizenry_units_to_unit_groups_junctions_tables`（`id` / `priority` / `unit` / `unit_group`）。

- 一行 = 一队驻军。想要两队同型兵就写两行。
- **验收**：进游戏守城，驻军列表与行数一致。

> ⚠️ 坑：`unit_group` 里填单位代码（如 `wh3_main_ksl_inf_kossars_0`）→ 该行静默失效，驻军不出现。它必须是 `armed_citizenry_unit_groups_tables` 的组 key。

## 8. 本地化键（后缀拼接规则）

| 对象 | 键格式 |
|---|---|
| 序列 tooltip | `building_chains_chain_tooltip_<chain>` |
| 建筑名称 | `building_culture_variants_name_<building>[<culture>][<subculture>][<faction>]` |
| 建筑简介 | `building_short_description_texts_short_description_<building>` |
| 建筑组名 | `building_sets_onscreen_name_<set>` |
| 建筑组说明 | `building_sets_onscreen_description_<set>` |

**名称后缀拼接**：`building_culture_variants_tables` 里填了哪几列限制，名称 key 就在建筑 key 后**按 culture→subculture→faction 顺序原样拼接**。WH3 实例：`building_culture_variants_name_wh3_main_sla_cult_3wh3_main_sla_slaanesh`（建筑 `wh3_main_sla_cult_3` + 派系 `wh3_main_sla_slaanesh`）。

- **简介键不拼后缀**，与名称不同。
- **验收**：`Select-String` 在 `<VANILLA>\local_cn\text\localisation__.loc.tsv` 里能搜到键名，且游戏内名称/简介非空。

> ⚠️ 坑：名称键漏拼 faction 后缀 → 游戏内显示键名原文或空白。

## 9. 城市模板表 = 版本更新重灾区

**WH3 表名已变**：教程 12 的 `slot_template_to_building_superchain_junctions_tables` 在 WH3 **不存在**，改用 `slot_template_permitted_building_chains_tables`（5 列：`chain` / `chain_set` / `slot_template` / `super_chain` / `remove`）。

- 三种接法（择一）：填 `super_chain` 把高级序列挂到某城市模板；或填 `chain` 直接挂单条序列；或填 `chain_set` 走 `building_chain_sets_tables`（`key` / `parent_set`）+ `building_chain_set_items_tables`（`chain` / `set` / `super_chain` / `remove`）做批量集合。
- 作者环境该表 1750 行；`slot_templates_tables` 只有 `key` / `resource` 两列（648 行）。
- **查某城市模板的方法**（教程 12 结论）：找该城市已有的原版地标建筑 → 取其 `building_superchain` → 在 `slot_template_permitted_building_chains_tables` 里搜该 superchain → 得到 `slot_template`。
- **作者原话（教程 12）**：CA 新 DLC 一动地图，这张表基本就要重填，**是版本更新重灾区**。
- **验收**：目标城市能建、且其他城市不被误开。


## 10. 加新科技：表清单与顺序

| # | 表 | 做什么 |
|---|---|---|
| 1 | `technologies_tables` | 注册科技 key、图标、唯一编号 |
| 2 | `technology_node_sets_tables` | 需要新科技组时才建（文化/子文化/派系限定） |
| 3 | `technology_nodes_tables` | 科技挂到节点，定 UI 位置/研究点/费用 |
| 4 | `technology_node_links_tables` | 节点串联线与箭头几何 |
| 5 | `technology_effects_junction_tables` | 科技效果 |
| 6 | `technology_required_building_levels_junctions_tables` | 前置建筑 |
| 7 | `technology_required_technology_junctions_tables` | 前置科技 |
| 8 | `technology_nodes_to_ancillaries_junctions_tables` | 科技给装备（**需脚本**） |
| 9 | `technology_ui_tabs_tables` ＋ `technology_ui_tabs_to_technology_nodes_junctions_tables` | UI 页归属（WH3 现行） |
| 10 | 本地化 | 名称/说明/UI 组名 |

**`technologies_tables` 只改三列**：`key`、`icon_name`、`unique_index`；其余照原版同类行（`building_level` 原版多为 `wh_main_chs_port_ruin`、`position_index` 多为 1、`info_pic` = `"placeholder.tga"`、`is_military` 勾选）。

**`technology_nodes_tables` 关键列**：`key` / `technology_key` / `technology_node_set` / `indent`（直列=Y）/ `tier`（横行=X）/ `research_points_required` / `cost_per_round` / `food_cost` / `resource_cost` / `optional_ui_group` / `required_parents` / `pixel_offset_x` / `pixel_offset_y` / `campaign_key` / `faction_key`。

- **Indent 是直列（Y 轴）、Tier 是横行（X 轴）**（教程 13）。WH3 实测：`indent` 取 −2…10（另有 998/999 隐藏节点），`tier` 取 0…30。隐藏科技用 998/999，不要硬填超范围值。
- 研究点费用是 `research_points_required`；金钱用 `cost_per_round`；派系资源用 `resource_cost`。
- **验收**：新科技出现在科技面板的正确行列；悬停显示费用与说明。

> ⚠️ 坑：把 `indent` 当横行、`tier` 当直列 → 科技线整片错位。核对法：读 `游戏原文件\db\technology_nodes_tables\data__.tsv` 表头，第 4 列是 `indent`、第 7 列是 `tier`。

## 11. 科技效果 / 前置 / 装备

- **科技效果**：`technology_effects_junction_tables`（`technology` / `effect` / `effect_scope` / `value`）。**Scope 一律是 `faction_to_*`**（科技由派系研究）。WH3 高频取值：`faction_to_force_own_unseen`、`faction_to_faction_own_unseen`、`faction_to_character_own_unseen`、`faction_to_province_own_unseen`、`faction_to_region_own_unseen`。
- **前置建筑**：`technology_required_building_levels_junctions_tables`（`technology` / `required_building_level`）。
- **前置科技**：`technology_required_technology_junctions_tables`（`technology` / `required_technology`）。
- **科技给装备**：`technology_nodes_to_ancillaries_junctions_tables`（`ancillary` / `technology_node`）。**光填表无效，必须写脚本**。WH3 现成范式：`游戏原文件\script\campaign\wh2_dlc11_tech_tree.lua`（监听 `ResearchCompleted` → `cm:spawn_character_to_pool(...)`）。脚本通用规则见 `40-Lua战役脚本.md`。
- **验收**：研究完成当回合效果生效；前置未满足时科技置灰。

> ⚠️ 坑：只填 `technology_nodes_to_ancillaries_junctions_tables` 不写脚本 → 研究完成后什么都没发生（教程 13 作者原注）。

## 12. 科技线几何参数

`technology_node_links_tables` 每行 = 一条箭头线。

| 列 | 填法 |
|---|---|
| `child_key` / `parent_key` | 箭头指向的节点 / 箭头出发的节点 |
| `initial_descent_tiers` | 原版全 0 |
| `parent_link_position` | 线接触**父节点**的面：1 上 / 2 右 / 3 下 / 4 左 |
| `child_link_position` | 线接触**子节点**的面：同上 |
| `parent_link_position_offset` / `child_link_position_offset` | 在该面上的偏移：−0.5（偏左/偏上）/ 0（居中）/ 0.5（偏右/偏下） |
| `visible_in_ui` | **WH3 新增列**，按原版填 `true` |

- **怎么看**：不要从节点视角看，从**线**的视角看——出发点是 `parent_key`，终点是 `child_key`，两个 `position` 分别看各自的接触面。
- 串联后的科技**自动成为前置科技**，不必再写 `technology_required_technology_junctions_tables`。
- **验收**：游戏内箭头从父节点正确面出发、接触子节点正确面，不穿过其他节点。

> ⚠️ 坑：把 `parent_link_position` / `child_link_position` 都按子节点填 → 箭头从错误的面出发，线穿过科技图标。

## 13. 科技 UI 分组（WH3 变化）

**WH3 现行做法**：科技节点归入 **UI 页（tab）**，用两表：

1. `technology_ui_tabs_tables`（`key` / `sort_order` / `tier_offset`）注册页；
2. `technology_ui_tabs_to_technology_nodes_junctions_tables`（`node` / `tab`）把节点挂进页。

**旧表仍在但只服务旧种族**：`technology_ui_groups_tables`（`key` / `optional_background_image` / `colour_hex`）＋ `technology_ui_groups_to_technology_nodes_junctions_tables`（`tech_ui_group` / `bottom_right_node` / `top_left_node` / `optional_top_right_node` / `optional_bottom_left_node`）。作者环境该组表 130 行，全部是帝国/高等精灵/蜥蜴人/巴托/混沌等前作种族；新种族（震旦/基斯里夫/恐虐/混沌矮人等）走 tab。`optional_ui_group` 仍对应 group。

- **怎么做**：先看目标派系的原版科技用哪套——在 `technology_ui_tabs_to_technology_nodes_junctions_tables` 里搜该派系节点，有命中就用 tab；否则才用 group（按 bounding box 填四个角节点，并在 `optional_ui_group` 回填组 key）。
- **验收**：新科技出现在正确的 UI 页/群组内，颜色与底图正确。

科技页归属按该种族当前 group/tab 结构核对；需要 tab 的科技须补 tab 关联，否则不会在对应页面显示。
