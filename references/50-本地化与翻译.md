## 0. 一页速览

1. **唯一真源**：`<VANILLA>\local_cn\text\localisation__.loc.tsv`（中文）+ 同源英文库；不查不写。
2. 键名 = **表前缀 + 完整键名**；前缀按表而异（`land_units_onscreen_name_`、`effects_description_`…），**逐表查证，不套模板**。
3. 换行一律写字面 `\\n`（**两个**反斜杠 + n，共 3 个字符），一条记录物理上必须是一行。
4. 专有术语**必须查原版库**；宁可不译（保留英文）也不机翻。
5. 文件编码：`localisation__.loc.tsv` 与 DB/`loc` TSV 实测均为 **UTF-8 无 BOM**（首字节 `6B 65 79` = `key`，非 `EF BB BF`）。
6. MOD 文本放 `mod/<MOD名>/text/db/<名>.loc.tsv`，首行固定 `key\ttext\ttooltip`。

## 3. 换行符：必须用字面 `\\n`（两个反斜杠 + n）

**规则**：本地化文本里的换行，统一写**字面 3 个 ASCII 字符**——两个反斜杠 `\` `\` + 字母 `n`。整条 TSV 记录**物理上必须是一行**。

| 写法 | 是什么 | 能否使用 |
|---|---|---|
| `\\n`（两个反斜杠 + n，三个字符） | 文件里的明文三字符，游戏解析后渲染成换行 | ✅ **唯一正确**（2026-09-13 实测：原版 CN 库 11,689 处全是双反斜杠，单反斜杠 0 处） |
| 真实换行控制符（LF） | 文件里真的断了一行 | ❌ 破坏 TSV 结构 |
| 物理换行（按回车写成多行） | 文件里真的多了一行 | ❌ 破坏 TSV 结构 |

真源实测样例（`localisation__.loc.tsv` 内字面 `\\n` 共 **11,689** 处；单反斜杠写法 **0** 处）：

```
campaign_payload_ui_details_description_dummy_wh2_dlc15_dragon_encounter_challenge_special	在龙巢中勇斗巨龙！此项行动会启动一次\\n神器任务战斗，为你带来更为丰厚的奖励	false
```

```tsv
-- ✅ 正确：字面 \\n，整条记录一行
effect_bundles_localised_description_xxx	第一段。\\n第二段。\\n第三段。

-- ❌ 错误：物理换行
effect_bundles_localised_description_xxx	第一段。
第二段。
```

- **怎么做**：落盘文件里必须是**两个反斜杠 + n**（3 个字符）。用 Node 写字符串字面量要敲 4 个反斜杠（`\\\\n`），用编辑器直接编辑就是敲两个反斜杠再敲 n；不要写真实换行。
- **验收**：`(Get-Content <file> | Measure-Object -Line)` 的行数 = 数据行数 + 2；同一条记录的物理行数必须为 1。

## 4. 术语查证流程（禁止机翻）

**核心**：所有人名、地名、物品、单位、法术等专有术语，**必须查原版翻译库**。宁可不翻译（保留英文），也不要机翻。

**两阶段，禁止跳过阶段一**：阶段一 术语预处理（提取 + 查库 + 替换），阶段二 句子翻译。

### 阶段一

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 逐句扫出所有专有术语，列清单（**宁多勿漏**） | 术语清单 |
| 2 | 模糊匹配术语库（忽略大小写 / 复数 / 定冠词 / 连字符 / 空格差异），命中即复用。**使用者未提供术语库时跳过，直接走 3** | 「英文 → 标准译名」映射表 |
| 3 | 未命中的术语：用**英文拼写**在中文库搜（英文常保留在 key 名与英文文本残留中），定位 key | 命中条目 |
| 3b | 用该 key 去中文库（`localisation__.loc.tsv`）查同 key 行，从中文文本提取官方译名 | 标准译名 |
| 3c | **强制**：把 `{英文, 中文, 出处 key}` 记入术语库（未提供术语库时记进 MOD 自己的 `README`） | 术语库增量 |
| 4 | 原版库查不到 → 联网查权威来源；仍查不到 → **保留英文原文** | 待查清单 |

### 4.3 key 反查法（作者环境替代方案，实测可行）

使用者没有独立英文库时，中文库本身也可当检索入口：专有名词的英文拼写常保留在 key 名里，中文库里也能搜到。

| 检索方式 | 实测示例 | 结果 |
|---|---|---|
| 用英文拼写搜中文库 | `Select-String -Path <loc> -Pattern 'Tirsyth' -SimpleMatch` | 命中 4 行，key 含 `wh_dlc05_wef_tirsyth`，值为"提西茨" |
| 用英文拼写搜中文库 | `Select-String -Path <loc> -Pattern 'Grimgor' -SimpleMatch` | 命中 125 行，中文为"格里姆格" |
| 用 key 直接查译名 | `ancillaries_onscreen_name_wh_main_anc_weapon_gitsnik` | "灭人斧" |

- **怎么做**：拿英文原名（或从 key 名反推的英文关键词）在中文库检索 → 取命中行的 key → 用该 key 精确检索 → 读中文值。
- **验收**：每个术语都能给出"英文 → key → 官方中文"三列证据。
- **局限**：英文库缺失意味着无法确认英文原文的**完整段落语境**（如拼写变体、同词异义）；此时必须以 key 名为准，并标注 `【未验证】`。

### 阶段二

术语映射表完整后才翻译整句：句中术语直接替换为映射表译名，普通英文词正常翻译。

**需要提取的术语类型**：人名/角色名/别称、地名/区域/城市/要塞、物品/武器/装备名、单位/兵种名、种族/派系/势力名、法术/技能/机制名。

**禁止事项**：

- ❌ 跳过术语提取直接翻译句子
- ❌ 查术语库只用精确匹配（忽略大小写/复数会漏命中）
- ❌ 用机翻翻译专有名词
- ❌ 想当然音译/意译术语
- ❌ 同一术语在不同条目译法不一致
- ❌ 查证了新术语却不回填术语库
- ❌ 把多个术语拼在一个正则里批量搜（漏命中且丢失 key 对应关系）
- ❌ 译文中夹带未查证的英文普通词

- **验收**：术语清单存在；每个术语都有"术语库命中"或"英文 → key → 官方中文"三列记录（§4.3）；译文里无长度 ≥ 4 的未翻译英文普通词。

## 5. 第三方 / 旧译本校对流程

**核心**：不能拿中文词直接搜原版库——中文词本身可能就是错的。必须"中文 → 英文 → 标准流程"绕回查证。

```
疑似译名（如"提尔赛斯"）
  │ A：找到该条目对应的英文原文（有英文源文件按 key 匹配；无则从 key 名反推关键词）
  ▼ B：从英文原文提取准确英文拼写（"提尔赛斯" → Tirsyth）
  ▼ C：走标准流程（步骤 2 术语库 → 步骤 3 中文库 key 反查）→ 官方译名"提西茨"
  ▼ D：与 mod 中文译文对比：一致 → 通过；不一致 → 替换为官方译名
```

**实测对照**（`factions_screen_name_wh_dlc05_wef_tirsyth` = "提西茨"）：旧译者凭音感自创的"提尔赛斯"看起来通顺，但与原版不符。

**批量校对策略**：

1. 从 mod 英文源文件提取所有大写专有名词
2. 每个英文专有名词走标准流程查官方 CN 译名
3. 在 mod 中文文件中搜索官方 CN 译名是否存在
4. 不存在 → 该条目用了错误译名 → 找出实际用了什么并替换
5. 存在 → 候选通过（仍需人工抽检，防止同词异译恰好撞上）

- **验收**：每个可疑译名都能给出英文原名 + 出处 key + 官方译名三要素。

## 5.5 扩展他人 pack 的汉化补丁（覆盖机制 + 文件名坑）

给别人的 mod 做汉化补丁时，**不只翻对文本，还要让覆盖真的生效**。

### 已采用方案：同路径完整覆写（2026-09-13 案例）

游戏按 **pack 内路径**取 loc：**路径逐字相同 → 高优先级 pack 的那份 .loc 整个顶掉低优先级的**，
不能只从以下案例推断所有不同路径 loc 的加载机制。该案例证据（拿 `!FanmoBretonniaCN.pack` 对拍源 mod）：

1. 文件名逐字相同：`effects__uber_brt_grail_virtues.loc`、`ibu_brt_name_land_units__.loc`…
   连 `ep_l'ordonnance_*.loc` 里的单引号都照抄。
2. 条目数逐一相等：8=8、16=16、36=36。

**推论**：汉化包里每个 loc **必须提供源 loc 的全部 key**（漏一条就在游戏里显示成空白或 key 名），
在此同路径覆写方案中，文件名必须与源**逐字相同**。独立 loc 文件按 key 覆盖是不同方案，其优先级与缺省行为需独立验证；当前工具的同路径覆盖检查不证明那一方案有效或无效。

### 坑：解包到磁盘的文件名会骗人

**源 mod 的 pack 内路径可能含 Windows 非法字符**。实测 `Morgiana_le_Fay_spell_rework.pack`
的 loc 在 pack 里叫 **`text/db/*Morgiana_land_units__.loc`**（星号开头，ASCII 42 排在字母数字前，
作者常用来让文件排最前）。

| 看法 | 看到的名字 |
|---|---|
| RPFM 解包到磁盘后 | `_Morgiana_land_units__.loc` ← **会骗人**（`*` 被静默替换成 `_`） |
| pack 内真实路径 | `*Morgiana_land_units__.loc` ← **真名** |
| 源 loc 第 2 行元数据 | `#Loc;1;text/db/*Morgiana_land_units__.loc` ← **铁证** |

**核对源 mod 的 loc 名，一律看 pack 内路径**（`查看.bat` / `inspect.js`）**或源 loc 的元数据行**，
不要相信解包后的磁盘文件名 —— 曾因此连错两版（`_` vs `*`），汉化完全不生效。

**怎么做**：磁盘上建不出带 `*` 的名字，用占位符 `__STAR__`，`rpfm-pack/pack.js` 打包时还原成 `*`：

```
text\db\__STAR__Morgiana_land_units__.loc.tsv   →   pack 内 text/db/*Morgiana_land_units__.loc
```

（`modcheck` 已同步支持该占位符，能正确做同路径对齐并在 `LOC_COVER` 里报出真实 pack 内路径。）

### 汉化补丁工作流

1. `inspect.js` 看源 pack 的 loc **pack 内路径** + `extract.js` 导出源 loc 作参考
2. 逐条翻译，**key 集合必须与源完全一致**（用 `modcheck --ref <源解包目录>` 验 `LOC_MISSING` = 0）
3. 磁盘文件名/路径与源**逐字对齐**（含 `*` 等特殊字符 → `__STAR__`）
4. 源 mod 若把英文直写进 DB 表（如 `character_skills_tables.localised_name`），游戏优先读 loc，
   需另补这些 key 的译文
5. 打包 → `inspect.js` 复核 pack 内路径与源逐字相同

> 多个源 mod 共用同一份 loc（如 Morganiana 的 `spell_rework` 与 `appearance`，实测两份 549 条
> key 与英文文本**逐字相同**）时，可各放一份同内容 loc，一次覆盖两个。

## 6. 编码规范（实测结论）

| 文件类型 | 编码 | 实测证据 |
|---|---|---|
| `localisation__.loc.tsv`（原版 CN 库） | **UTF-8 无 BOM** | 首 16 字节 `6B 65 79 09 74 65 78 74 09 …`（`key\ttext\t`），无 `EF BB BF` |
| DB `data__.tsv` | **UTF-8 无 BOM** | `effects_tables\data__.tsv` 首字节 `65 66 66 65 63 74`（`effect`） |
| MOD `db/*.tsv`、`text/db/*.loc.tsv` | **UTF-8 无 BOM** | `参考mod\laf\text\db\laf_crank_gunners__.loc.tsv`、`已完成mod\su_heimache\db\land_units_tables\su_heimache.tsv` 等首字节均为 `6B 65 79`，无 BOM |

- **结论**：本地化与 DB 文本一律 **UTF-8 无 BOM**。
- **怎么做**：用不自动加 BOM 的编辑器/工具写；写入后检查首 3 字节。
- **验收**：`[System.IO.File]::ReadAllBytes($p)[0..2]` 不等于 `EF BB BF`；RPFM 导入正常；游戏内中文不乱码。

> ⚠️ 坑：照抄 `tsv_format.md` 的"UTF-8 with BOM（RPFM 默认）" → 与真源实测不符；作者环境实测原版与现有 MOD 文件**全部无 BOM**，以本册 §6 为准。
> ⚠️ 坑：Lua 脚本带 BOM → `luac5.1.exe` 报 `near '�'`（见 `40-Lua战役脚本.md` §2）。

## 7. 反面案例（错误做法 → 后果）

| 错误做法 | 后果 |
|---|---|
| 把多个术语拼进一个正则批量搜 | 只命中一两个就误判"已查证"，`Iron Dragon`、`Dawi-Zharr`、`Tiger Court`、`House of Secrets` 等全部漏查 |
| 跳过"用 key 查中文库"，凭印象改译 | `Iron Dragon` 被译成"铸铁龙"，官方译名实为**镔龙** |
| 专有名词保留英文不查证 | `Dawi-Zharr` 原样留英文，官方译名实为**扎尔矮人**（漏翻） |
| 把概念词当"诗化标题"擅自改名 | `Heavenly Bowman` 官方别称**天穹射手**，被改成"苍天弓神"，玩家无法对应 |
| 译文夹带未查证英文普通词 | 出现 `gibbering 的恶魔`、`razor 锋利的爪刃`、`hamstring 了一头`、`炮兵 crews` 等中英混杂 |
| 武器名括注凭印象 | `Gitsnik` 括注"（碎颅者）"，官方译名实为**灭人斧** |
| 用中文词直接搜原版库判断对错 | "提尔赛斯"看似通顺，英文 `Tirsyth` 官方译名实为**提西茨** |
| 把完整键名当本地化键 | 游戏查不到，显示为空或键名原文 |
| 用真实换行代替字面 `\\n` | TSV 记录被拆行，导入报错或文本错乱 |
| 汉化补丁的 loc 名照抄"解包到磁盘"的文件名 | 源 pack 内真名可能带 `*`（磁盘上被替换成 `_`），差一个字符就**完全不覆盖**，汉化看着做了却不生效（§5.5） |
| 汉化补丁只翻一部分 key | loc 是**整文件替换**，源 loc 里没被覆盖的 key 全部回落成空白或 key 名（§5.5） |

## 8. 自检清单

- [ ] 所有本地化键名遵循「表前缀 + 完整键名」，前缀**逐表**查证过（尤其建筑用 `building_culture_variants_name_`）
- [ ] 建筑变体键的四段拼接顺序正确（`building`+`culture`+`subculture`+`faction`，无分隔符）
- [ ] 换行全部是字面 `\\n`（两个反斜杠 + n，三字符），无物理换行、无真实换行控制符；每条记录物理一行
- [ ] 先提取术语清单，再翻译句子
- [ ] 每个专有术语都模糊匹配过术语库（忽略大小写/复数），命中即复用；术语库不存在时已直接走 §4.3
- [ ] 术语库未收录的新术语已走完「英文 → key → 官方中文」流程（§4.3）
- [ ] 新确证的术语已记入术语库（使用者无术语库时记进 MOD 的 `README` 或新建该文件）
- [ ] 全文扫描无夹带的未翻译英文普通词（长度 ≥ 4 的英文词逐一确认）
- [ ] 同一术语在所有条目中译名一致
- [ ] 文件为 UTF-8 无 BOM；首行 `key\ttext\ttooltip`；元数据行 `#Loc;1;text/db/<文件名>`
- [ ] RPFM 导入无报错，游戏内显示中文而非键名
