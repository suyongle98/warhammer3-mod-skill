# 44 · 伪源码整理与机制还原

> 适用：WH3 Lua / TWUI / CCO 与原生机制分析；案例来自 WH3 9.0.4.0。
> 事实截止：2026-10-21（文档整理）；来源：2026-10-17～20 狐女小屋历史案例的静态审计与定向反编译摘要；公开版的证据边界见 §6。
> 边界：伪源码是带证据的机制模型，不是 CA 原始源码，也不是已经可以编译的业务源码。本次没有新增游戏内验证。

## 1. 何时使用

当需求横跨 DB、布局、CCO、Lua 和 DLL，或只有二进制而缺失原业务源码时，先把关键路径还原为可核查的伪源码。只整理当前问题所需的函数和状态，不整包翻译反编译输出。

已有原版 Lua 是实际源码，应直接引用；CCO 表达式保留求值上下文；Ghidra 的 C 输出是工具推断；人工命名和简化后的流程是分析模型。这四种材料分别标识。需要取得原生证据时转 [61-原生反编译与版本适配](61-原生反编译与版本适配.md)；组件生命周期和布局格式仍查 `43`。

## 2. 从一个操作还原完整路径

先选能复现的单次操作，如“选择组合”“点击制造”“读档后再次制造”，记录输入、预期输出和实际差异，再依次追踪：

| 层 | 要找的证据 | 需要回答的问题 |
|---|---|---|
| DB | 当前原版与 MOD 同类记录、关联表、schema | 谁被授权、如何匹配、费用与效果来自哪里？ |
| TWUI | pack 内实际路径、控件、事件与回调 | 点击触发什么？谁刷新图片、按钮和列表？ |
| CCO | 表达式、ContextPropagator、依赖事件 | 查询对象是谁？选择、显示、可制造是否使用同一条件？ |
| Lua | 入口、监听器、API 调用、保存/加载回调 | 谁校验并发起操作？异常是否阻断后续初始化？ |
| 原生 | 导出注册、函数体、调用者、参数和状态写入 | 最终写了库存、当前成品还是进度？是否派发共享事件？ |
| 持久状态 | saved value、引擎模型、模块级变量 | 哪些会存档，哪些只活到关面板、销毁 Lua 状态或退出进程？ |

制作前校验、执行动作、成功后的扣费/冷却、失败路径及清理都应落到来源。显示正确只能证明显示层；列表隐藏不能证明记录退出自动匹配；入库成功不能证明共享事件没有触发。

把“无同路径文件覆盖”“无运行时改写”“无共享数据或事件副作用”分别列为兼容目标；改动只有一行仍可能覆盖整个原版文件。不要把少量 diff 或加了命名空间当成完整隔离证据。

## 3. 伪源码的写法与证据账本

每段注明输入文件 SHA256、游戏版本、源位置（源码路径/函数/RVA）、分析日期和未闭合部分。函数名有符号或注册字符串依据时写原名；人工语义名明确标为“分析命名”。参数类型、所有权、返回值未证实时保留未知项，不能靠命名补齐。

建议采用以下最小记录，字段可按问题增减：

| 项 | 写法 |
|---|---|
| 身份 | EXE/DLL 的 SHA256、大小、image base；Lua/布局的 pack 内路径与提取来源 |
| 输入/输出 | 对象、单位 id、材料、返回码或状态变化；未知类型直接注明 |
| 顺序与状态 | 校验 → 调用 → 写入 → 事件 → 清理，标出每个分支 |
| 证据 | 原文件与行号、函数范围、RVA、指令或日志；大段 dump 留项目 `_work/` |
| 结论层级 | `源码事实`、`指令事实`、`分析推断`、`游戏实测`；给出覆盖范围 |
| 待验 | 缺失调用者、间接调用、运行时对象身份、存读档或第三方组合 |

以下是作者案例静态证据的缩写，**仅用于说明模型，不可复制为当前版本的生产定位代码**。来源：历史模型根研究的指令摘要；输入版本身份见 `61` §6，原始 dump 不随包提供。

```text
// 分析命名；read_ptr 表示读取指针，不是游戏 API。
root_slot_rva = resolve_from_two_verified_instruction_paths()
root = read_ptr(runtime_image_base + root_slot_rva)
manager = read_ptr(root + 0x6ca0)
cooking = read_ptr(manager + 0xd8)

units = read_ptr(root + 0x5bb8)
unit = lookup_unit(units + 0x80, address_of(id))
// 当前指令静态闭合；跨档对象有效性、返回对象业务身份另验。
```

槽地址、槽内指针和最终对象分别记录。数值偏移只属于该输入版本，不能因进入技能书就成为长期常量。伪源码中的解引用省略了错误处理；落地实现需逐层检查对象可读、空值及生命周期。

## 4. 从狐女小屋提炼的三种分析方法

### 4.1 选择、显示与制造分开建模

历史配方选择与 CCO 案例表明：允许选择某配方、采用它做预览、允许实际制造，是三个决策。材料不足时保留所选配方并禁止制造，可以只调整选择分支；实际材料数、解锁槽、冷却与费用仍由执行端检查。

同理，“点组合不刷新，制作后才刷新”应追踪传播器的监听事件。本例布局依赖 `ingredient_selected`，移除自动填材料回调也移除了间接刷新。要修的是选择事件到预览的依赖，不应恢复用户已取消的自动填材料。重新打开面板的选择规则单独核对，不从打开期间的规则推导跨面板持久化。

### 4.2 列表过滤、配方匹配、事件与库存分开建模

历史自动配方匹配案例记录：小屋配方退出显示列表后，仍能成为原生自动匹配候选。为自有配方设置不可获得的内部匹配要求，可以阻断该数据路径；须同时核对所选配方的显式制作入口是否绕过该要求。

该案例的离线枚举覆盖 22,750 种原版咕噜食材搭配，不能推广为第三方食谱或真实引擎的全部行为。事件消费者、当前菜肴、库存、进度和旧档迁移分别验收；“制造结果正确”不意味着任务、特质与共享事件未受影响。

### 4.3 生命周期按对象层次拆开

历史适配器案例记录同进程读档时定位失败：第一次安装的 hook 改了内存函数入口，第二次再扫描入口就失配。区分磁盘 EXE、实时映像、DLL、Lua 状态和战役模型实例，才能还原故障发生的阶段。

从磁盘定位 RVA，再以实时模块基址解析对象，可以避免把自身入口改写当成版本变化；但仍须核对磁盘与已加载模块身份，不得跨档缓存模型实例。是否复用 DLL、何时撤销 hook、异常后哪些服务继续运行，均列成显式状态转移；钩子归属边界见 `61` §5。

## 5. 验收

- [ ] 任一关键分支都能回到源码、机器指令或日志；人工命名不冒充官方符号。
- [ ] 对象层级、校验与执行、显示与匹配、状态写入和事件副作用分别说明。
- [ ] 成功、拒绝、异常、中途失败、关面板、同进程读档均有对应路径或明确待验项。
- [ ] 离线模型的假设和覆盖范围写明；模拟通过没有写成真实引擎通过。
- [ ] 通用方法在技能书；具体配方、地址全集、dump、脚本与迁移记录仍保留在项目内。

## 6. 分享版证据边界与复现材料

本册提炼历史案例的方法，不分发个人日志、项目工作目录、完整反编译 dump、游戏二进制或分析工程。案例中的数字和静态观察只代表当次输入，不是本次发布重新验证的结果；不依赖读者取得作者的私人文件。

复现自己的问题时，在自选的分析目录保留：输入身份、原版与 MOD 差异、关键函数/指令、事件及状态变化、实际执行过的检查和未闭合问题。原生输入身份与地址规则见 [61](61-原生反编译与版本适配.md)，游戏资料版本见 [05](05-版本维护与核验.md)。缺少对应原始证据时，将历史案例当作定位线索，不能当作自己版本已经证实的机制。
