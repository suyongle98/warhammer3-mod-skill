## 0. 一页速览

1. MOD 目录 = `db\` + `script\` + `text\` + `ui\`（+ 兵种类的 `variantmeshes\` / `animations\` / `warmachines\`）。
2. DB 按完整文件路径覆写文件、按主键合并不同文件的行；避免与源文件撞路径。
3. 导入原版表后**删掉不改的行**；**绝不直接改游戏原文件**。
4. 默认交付源文件；已获打包授权时用 `rpfm-pack/pack.js`。部署/发布另按授权范围。
5. 覆盖方向：管理器列表**上方覆盖下方**同词条。
6. 工坊上传要 `pack` 与封面 PNG **同名同目录**，封面 ≤1 MB、正方形；最后把可见性设为**公开**。
7. 游戏更新/DLC 后先 `Check Schema Updates`，再逐表核对**表头与版本号**。

## 1. MOD 目录结构

```
<MOD目录>\
├── db\<表名>_tables\<文件名>.tsv        # 表名目录必须与原版同名（含 _tables 后缀）
├── script\campaign\mod\<前缀>_<功能>.lua # 战役 Lua（新功能）
├── script\mct\settings\<前缀>_MCT.lua    # MCT 配置菜单（可选）
├── text\db\<前缀>_<名>.loc.tsv           # 本地化（列头固定 key/text/tooltip）
├── ui\battle ui\ability_icons\*.png      # 技能图标
├── ui\campaign ui\ancillaries\*.png      # 装备/战旗图标
├── ui\units\icons\、ui\units\infopics\   # 兵牌、单位详情图
├── variantmeshes\、animations\、warmachines\   # 兵种类的模型/动画/战争机器
└── settings.rpfm_reserved.json           # RPFM 打包设置（压缩格式）
```

- **怎么做**：建 MOD 时先照上表建空目录；`db` 下的表目录名从 `游戏原文件\db\` 原样复制。
- 实例对照：`<MODS>\su_qizhi\打包版\`（`db\` 27 张表 + `text\db\` 6 个 loc + `script\campaign\mod\su_qizhi_mission_chain.lua` + `ui\campaign ui\ancillaries\`）；`<REFERENCE>\laf\`（含 `animations\`、`variantmeshes\`、`settings.rpfm_reserved.json`）。
- **验收**：`Get-ChildItem -Recurse <MOD目录>` 的顶层只有上表列出的目录；每个 `db\` 子目录名都能在 `<VANILLA>\db\` 中找到同名目录。

> ⚠️ 坑：`ui\battle ui`、`ui\campaign ui` 中的空格被删掉或改写 → 引擎找不到资源，图标不显示。

## 2. DB 文件覆写与行合并

**分两层核对**：同一 pack 内完整路径的文件由高优先级 pack 覆写；同表目录下不同文件的数据行参与合并，主键冲突时受处理优先级影响。`data__` 是原版常见文件名，不是识别全库加载模式的特殊开关。

| 写法 | 影响与用途 |
|---|---|
| 独立自定义文件名 | 保留其他文件的行；新增 key 可加入，覆盖原 key 还需验证优先级 |
| 与原版/父 MOD 完整路径同名 | 覆写那一个文件；没保留的行从该文件消失，其他文件仍可能提供同 key |
| `!`、数字或其他前缀 | 影响命名/处理优先级，不产生增量/替换两种格式；避免只靠前缀推断跨 MOD 结果 |
| 删除指定原版行 | 当前 WH3 可用 `twad_key_deletes_tables`，见 `15` §3.3；不能把整表副本作为默认删行手段 |

只改必要行并使用 MOD 专属文件名；为覆盖选取有明确差异的值，在当前加载组合中实测。RPFM 作者机制说明见 `05` §5，本次未重新做加载优先级的游戏实测。

DB 元数据为第 2 行 `#<表名>;<schema版本>;<pack内完整路径>`，路径不带 `.tsv`；loc 为 `#Loc;1;text/db/<名>.loc`。导出可能以空 tab 补齐元数据列，保留合法空字段。版本、列序从当前同表 TSV 取。

验收：pack 内实际路径与元数据一致，自定义文件名没有无意碰撞；数据行列数正确；覆盖意图和删除引用均明确。

## 3. 导入与改动纪律

- **绝不直接改游戏原文件**：所有修改先导入自己的 pack 后再改（教程 01 连写三遍"千万别直接修改游戏原文件"）。
- **导入后删除不修改的行**：RPFM 里 `Shift`/`Ctrl` 加左键多选 → `Delete`。多余行只造成 MOD 兼容问题。
- **怎么做**：RPFM 打开原版 pack（如 `db.pack`）→ 右键表 `Extract`/`Add > From PackFile` 导入到自己的 pack → 重命名子表 → 删掉不改的行 → 改值。
- 常用右键项：`Add Row` 加行、`Insert Row` 插入行、`Clone` 克隆行、`Paste`（可贴成新行 / 贴到选取格）、`Undo`/`Redo`。
- 改前留备份：实例做法是整目录备份到 `su_qizhi\_xls_work\backup_打包版\`。
- **验收**：`游戏原文件\` 与 `...\Total War WARHAMMER III\data\` 下的原版 pack 修改时间未变；MOD 目录里每张表只含你要改/新增的行。

## 4. pack 打包流程（已获打包授权时）

按使用者目标交付源文件或 pack。已获打包授权时，先自检，再用现成 `rpfm-pack/pack.js` 生成工作区产物；部署到游戏与工坊发布按用户授权范围执行。GUI 只用于交互查看或脚本未覆盖的操作，不作为自动化默认路线。

- **打包前必做自检**：`node "<SKILL>\tools\modcheck\check.js" <MOD目录> --vanilla "<VANILLA>\db"`——编码/BOM、**表头与版本对拍原版真源**、元数据行、列数、主键重复、loc 转义与漏翻、**跨表引用闭合（抓拼错的 key）**；退出码 0 再打包。汉化包/扩展别人 pack 的补丁包必须加 `--ref <参考mod解包目录>`。详见 `../tools/modcheck/README.md`。
- **随包脚本做法**：**命令行一键打包** =
  `node "<SKILL>\tools\rpfm-pack\pack.js" <MOD目录> [输出.pack]`
  （自动拉起 `rpfm_server` → 建表 → 导 TSV → 存 pack，自动排除 `_work/`、`打包版/` 等；目录名的 `@` 前缀默认去掉，要保留就显式传第二个参数）。查看/解包/对比用同目录 `inspect.js` / `extract.js`。
- **文件名占位符 `__STAR__`**：pack 内路径可能含 Windows 非法字符（实测源 mod 的 loc 就叫 `text/db/*Morgiana_land_units__.loc`），磁盘上建不出这种名字 —— 约定**磁盘文件名写 `__STAR__`，`pack.js` 打包时还原成 `*`**。
  ⚠️ 反向的坑：**RPFM 解包到磁盘时 `*` 会被静默替换成 `_`**，所以核对源 mod 的文件名必须看 **pack 内路径**（`inspect.js`）或 loc 元数据行，**别信解包后的磁盘名**（详见 `50-本地化与翻译.md` §5.5）。
- **边界**：RPFM v5.0.6 自身没有独立 CLI，命令行打包走上面的 `rpfm_server` HTTP/MCP 通道（`rpfm-pack` 就是这个通道的封装）。
- **验收**：`...\data\<英文名>.pack` 存在；RPFM 打开该 pack 能看到 `db/…`、`script/…`、`text/…`、`ui/…` 结构；游戏启动后 MOD 出现在管理器列表。

- **打包后回环验证（三步，2026-09-23 `su_qbzx` 实操）**：打包后把 pack 解包回来与源文件逐行比对，能抓出源文件看不出、进游戏才发现的问题。
  1. 打包：`node "<SKILL>\tools\rpfm-pack\pack.js" <MOD目录>`
  2. 解包：`node "<SKILL>\tools\rpfm-pack\extract.js" "<MOD目录>\打包版\<名字>.pack" <临时目录>`
  3. 比对：逐文件比对源与解包结果（文本按行、图片按 SHA256）。**允许的差异只有元数据行**——RPFM 导出时会把第 2 行补齐到与表头相同的列数（补空 tab）；数据行必须逐行一致。
  - 常见必须复检的点：`ui\battle ui\…`、`ui\campaign ui\…` 目录名里的**空格**是否原样保留；loc 是否为 `text/…/<名字>.loc`（源文件在磁盘上是 `.loc.tsv`）；pack 内是否混入了不该进的目录（`_verify\`、`_work\` 等，`pack.js` 只排除固定清单，自建临时目录要放在 MOD 目录**之外**）。

> ⚠️ 坑：pack 文件名用中文 → 游戏静默不加载（教程 01 强调"不能是中文"）。
> ⚠️ 坑：pack 名与封面图名不一致 → 创意工坊上传失败（见 §6）。

## 5. MOD 加载顺序与冲突

同路径文件冲突先查管理器加载与 pack 依赖；不同 DB 文件的同 key 冲突还涉及文件处理优先级。`!` 等前缀提供命名排序线索，不能单独证明最终跨 MOD 覆盖方向。现有案例使用“补丁排到源 MOD 上方”的组合，若引擎/管理器更新，应取两个差异明显的值，在实际组合中验证；本次没有重做游戏加载顺序实验。

- 作者环境加载清单格式（`...\Total War WARHAMMER III\wyccc_launch_mods.txt`）：
  ```
  add_working_directory "<WORKSHOP>\<modid>";
  mod "!!!!wyccc_unit_data_patch.pack";
  mod "su_shiyan.pack";
  ```
  `add_working_directory` 把工坊目录加入搜索路径，`mod` 行顺序即加载顺序；`!!!!wyccc_unit_data_patch.pack` 位于 `mod` 行首位。
- 冲突定位：RPFM 分别打开两个 pack，对比同一张表同一 key 的行，改到只剩一处生效。
- **验收**：游戏内实际生效的是排在上方的 MOD 的值；同一词条不会出现"改了这个 MOD 另一个 MOD 失效"的意外。

> ⚠️ 坑：以为"先加载的被后加载覆盖" → 实际是**上方覆盖下方**（教程 01 评论区作者确认）。

> ⚠️ 坑：以为 WH3 只读 `data` 目录里的 pack（教程 16 的 WH2 结论）→ 作者环境加载清单用 `add_working_directory` 直接加载工坊目录，两个来源都生效；改 MOD 前先确认目标 pack 在哪个目录。

## 6. 创意工坊上传

### 6.1 封面 PNG 规范

| 项 | 要求 | 作者环境实证 |
|---|---|---|
| 格式 | PNG | 工坊目录里每个 MOD 都是 `<pack名>.pack` + `<pack名>.png` 成对 |
| 文件名 | **与 pack 同名**（`@123.pack` → `@123.png`） | `skulls_just_more_items.pack` 配 `skulls_just_more_items.png` |
| 位置 | 与 pack **同一目录**（`data` 目录 / 工坊 MOD 目录） | 同上 |
| 大小 | **≤ 1 MB** | 遗留封面 `data\su_shiyan.png` = 842,395 B（823 KB） |
| 形状 | 正方形 | 上述遗留封面为 968×549，非正方形；教程 16 把正方形列为推荐项而非硬性要求 |

- **怎么做**：用 `magick identify <封面>` 查尺寸与体积；超限用 `magick <in> -resize 512x512 <out>` 压到正方形。
- **验收**：`magick identify` 输出 `PNG`、宽 = 高、文件 < 1 MB，且文件名与 pack 去扩展名后完全相同。

### 6.2 上传步骤（教程 16，WH2 环境）

1. 把 `.pack` 放到游戏 `data` 目录。
2. 准备封面 PNG（§6.1 规范），与 pack 同目录。
3. 打开官方启动器，找到该 MOD，点旁边的蓝色文件夹图标上传。
4. 选择分类、同意创意工坊协议，等上传完成。
5. 填写说明文字与图片。
6. **把可见性设为公开**。

- **失败常见原因**：封面图片不符规范（最常见）；网络需要加速器。
- **教程给的 WH2 路径必须换成 WH3**：`Steam\steamapps\common\Total War WARHAMMER II\data` → `<GAME>\data`；工坊 `workshop\content\594570\` → `workshop\content\1142710\`。
- **【未验证】**：作者环境 WH3 官方启动器（`...\Total War WARHAMMER III\launcher\launcher.exe`）的上传入口与"更新已发布 MOD"的界面流程未经实测；教程 16 全流程为 WH2 环境。上传前先与用户确认入口。
- **【未验证】**：作者环境同时装有第三方管理器 TWMM（`...\twmm\twmm.exe`），其与官方启动器的上传入口是否互通未经实测。

## 7. 游戏更新 / DLC 后的维护流程

| 步骤 | 操作 | 验收 |
|---|---|---|
| 1 | RPFM `About > Check Schema Updates` 更新 schema；失败按 `02-环境与工具.md` §5.2 排错 | 无错误弹窗 |
| 2 | 打开 MOD 的表，RPFM 会提示哪些表已过时 | 过时表清单已知 |
| 3 | 对照 `<VANILLA>\db\<表名>_tables\data__.tsv` 的**表头 + 元数据版本号**逐栏核对 | 列名与顺序、版本号一致 |
| 4 | 缺列补齐（值照原版同类行）、多列删除；引用字段按新列名改 | 列数 = 表头列数 |
| 5 | 跑 `modcheck` 自检：`node "<SKILL>\tools\modcheck\check.js" <MOD目录> --vanilla "<VANILLA>\db"`（表头/版本号对拍原版 + 引用完整性 + loc 覆盖）—— 旧的项目内脚本 `su_qizhi\_xls_work\validate_mod.ps1` 已由它的通用版取代 | 退出码 0；「表头与原版一致」数 = 表数；无 DANGLING/漏翻警告 |
| 6 | 重新打包 → 进游戏实测 | 目标功能生效，原版功能未坏 |

- **已实证的失败案例（WH3）**：`su_qizhi` 的自建被动在游戏内**全部无效**，根因是 3 张表按 WH2 旧 schema 编写、表头与版本号落后于 `data.pack`，RPFM 按旧版本导入后游戏不识别这些表。修复对照：

| 表 | 旧版本 → 新版本 | 改动 |
|---|---|---|
| `special_ability_phases_tables` | 42 → 44 | 表头去掉 `unbreakable`，末位补 `execute_ratio` |
| `unit_special_abilities_tables` | 72 → 74 | 列名 `align_orientation_to_target_unit` → `audio_vo_actor_override`；`behaviour` 留空，`autoresolver_usage` 用枚举（`buff_self`/`debuff_unit`），不再用 WH2 数字 |
| `rituals_tables` | 2 → 4 | 表尾补 `influence_cost`（0）、`max_times_cost_can_increase`（2147483647） |

- **新增字段跟进**：原版表头多出的列必须在自己的 TSV 里补齐（哪怕填空/照原版同类行值）；少列会被 RPFM 拒绝或列错位。
- **验收**：`modcheck` 的表头与版本提示均经复核；游戏内改动生效。

> ⚠️ 坑：照抄旧版本 MOD 的表头与版本号 → 该表整表不加载，效果静默失效且**无报错**（本次案例的真实后果）。

## 8. 验收清单

- [ ] MOD 目录只有 `db\` / `script\` / `text\` / `ui\`（及兵种类的 `variantmeshes\` 等），`db\` 子目录名与原版一致
- [ ] 每张表使用独立文件名；有意同路径覆写或删行已核对影响（§2）
- [ ] 元数据行格式 `#表名;版本号;表路径`（路径不带 `.tsv`），版本号与 `游戏原文件` 一致
- [ ] 导入后已删除不修改的行
- [ ] 未直接修改 `游戏原文件\` 与游戏 `data\` 下的原版 pack
- [ ] 若用户授权部署，pack 已用现成脚本打包并落到 `<GAME>\data`，文件名无中文
- [ ] 需要覆盖其他 MOD 时，本 MOD 在管理器列表中的位置在对方上方
- [ ] 封面 PNG 与 pack 同名同目录、≤1 MB、正方形（上传前）
- [ ] 若用户授权工坊发布，确认上传成功和指定可见性
- [ ] **已跑 `modcheck` 且退出码 0**（`node "<SKILL>\tools\modcheck\check.js" <MOD目录> --vanilla "<VANILLA>\db"`；汉化包/补丁包加 `--ref <参考mod解包目录>`）
- [ ] 若用户授权打包，已用 `rpfm-pack\pack.js` 打包，产物能解包回来与源逐文件一致
- [ ] 游戏更新/DLC 后已过一遍 §7 六步，`modcheck` 报的表头/版本问题全部清零
