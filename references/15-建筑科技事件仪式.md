## 0. 读法

**本册是表字典**：只讲表、字段、主键、关联、坑。做法（新建建筑/科技/事件/仪式、Lua 触发）见 `24-建筑与科技.md`、`40-Lua战役脚本.md`。

查表三步法：① 在 `游戏原文件\db\` 找 `<表名>_tables\` → ② 读 `data__.tsv` **第 1 行**表头（第 2 行 `#表名;版本;db/...` 是元数据）→ ③ 抄一条原版同类行做基准。条目格式：`表名 — 用途`；`PK`=主键；`←`=被谁引用，`→`=引用了谁。

## 1. 反向索引：想做 X → 查哪几张表

## 2. 建筑域

```
building_superchains_tables   超级链（只有 key）
 └ building_chains_tables      链（category / superchain / 外槽标记 / 可否拆）
    └ building_levels_tables     等级（成本·资源·实例·UI）
       ├ building_effects_junction_tables                 效果（直挂 effect，不走 effect_bundle）
       ├ building_culture_variants_tables                 文化/派系变体（图标·描述·外观）
       ├ building_units_allowed_tables                    解锁招募
       └ building_level_armed_citizenry_junctions_tables  武装市民
```

- `building_superchains_tables` — 超级链归类。PK `key`（仅一列）。← `building_chains.building_superchain`
- `building_chains_tables` — 建筑链。PK `key`。改动：`chain_category`、`building_superchain`、`is_foreign_slot_chain`、`can_be_dismantled`。← `building_levels.chain`、`building_set_to_building_junctions`
- `building_levels_tables` — 等级主表。PK `level_name`。改动：`chain`、`level`、`create_cost`、`upkeep_cost`、`food_cost`、`resource_cost`、`only_in_capital`、`can_convert`、`building_instance_key`、`visible_in_ui`。← effects / culture_variants / units_allowed / slot_set_items / `technologies_tables.building_level`
- `building_effects_junction_tables` — 建筑效果。PK `building`+`effect`。列：`effect_scope`、`value`、`value_damaged`。→ `effects_tables.effect`
- `building_culture_variants_tables` — 文化/派系变体。PK `building`+`culture`/`subculture`/`faction`。列：`icon`、`description`
- `building_sets_tables` / `building_set_to_building_junctions_tables` — 建筑集（PK `key`；`icon`、`sort_order`、`show_in_ui`）/ 集↔链或等级（PK `building_set`+`building_chain`/`building_level`；`exclude`）
- `building_chain_availability_set_ids_tables` / `building_chain_availability_sets_tables` / `building_chain_availabilities_tables` — 可用性集 id 池（PK `id`）/ 链↔集 id（PK `building_chain`+`id`）/ 明细（PK `id` 数字；`set_id`、`culture`、`faction`、`sub_culture`、`campaign`，全空=不限）
- `building_units_allowed_tables` — 解锁招募。PK `key`（数字）。列：`building`、`unit`、`XP`、`conditions`、`faction`、`enabled`。→ `main_units_tables.unit`
- `building_level_armed_citizenry_junctions_tables` — 等级↔守军单位组。PK `id`。列：`building_level`、`unit_group`
- `slot_set_items_tables` / `slot_templates_tables` / `slot_types_tables` — 槽位项（PK `id`；`slot_template`、`slot_type`、`slot_set`、`building_level`）/ 槽模板（PK `key`）/ 槽类型（PK `key`）
- `settlement_type_to_building_chains_junctions_tables` — 定居点类型可建哪些链。PK `building_chain`+`settlement_type`；`exclude` 反向排除

> ⚠️ 坑：建筑效果写进 `effect_bundles_to_effects_junctions` → 不生效。建筑效果**直挂** `building_effects_junction_tables`。
> ⚠️ 坑：`effect_scope` 随手填 → 加成传导错层级。原版高频值：`region_to_region_own`(5236)、`building_to_building_own`(2667)、`this_building`(705)。
> ⚠️ 坑：以为 `building_levels_tables.resource_requirement`（列 10）管资源消耗 → 原版 5259 行**全空**（`commodity` 列 6 同样全空）；资源消耗实际走 `resource_cost`（列 22，395 行有值）。
> ⚠️ 坑：以为 `building_units_allowed_tables.enabled=true` 才是"启用" → 原版 6396 行 `enabled` **全为 `false`**、`conditions` 全为 `0`、`faction` 全为空；语义未证实【未验证】，**照抄原版同类行**。

## 3. 事件 / 两难 / 任务域

分工：`incidents`（通知，单选项/无选项）、`dilemmas`（多选一）、`missions`（有目标，可成功/失败）；三者共享 `cdir_events_*` 载荷系统。

- `incidents_tables` — 事件通知。PK `key`。改动：`generate`、`event_category`、`ui_image`、`is_large_incident`、`prioritised`
- `dilemmas_tables` — 两难。PK `key`。改动：`generate`、`event_category`、`localised_title`/`_description`、`ui_image`、`prioritized`、`is_large_dilemma`
- `missions_tables` — 任务。PK `key`。改动：`mission_type`、`localised_title`/`_description`/`_mission_completed_text`、`event_category`、`quest_mission`/`_final`、`trigger_radius`

> ⚠️ 坑：`prioritised`（s）与 `prioritized`（z）**拼写不一致**：`incidents`/`missions` 用 `prioritised`，`dilemmas` 用 `prioritized`。抄错列名 → 导入报错或列错位。

### 3.1 载荷系统

- `cdir_events_payloads_tables` — 合法 `payload_key` 白名单（34 条）。PK `payload_key`。← 三张 `*_payloads_tables.payload_key`
- `cdir_events_incident_payloads_tables` — 事件载荷。PK `id`。列：`incident_key`、`payload_key`、`value`、`target_key`
- `cdir_events_dilemma_payloads_tables` — 两难载荷。PK `id`。列：`choice_key`、`dilemma_key`、`payload_key`、`value`、`target_key`
- `cdir_events_mission_payloads_tables` — 任务载荷。PK `id`。列：`mission_key`、`payload_key`、`status_key`、`value`、`target_key`

**载荷 key 语法（实测原版数据行）**：`payload_key` 是**大写枚举**，参数写在 `value` 列的 `KEY[...]` 分号串。

| `payload_key` | `value` 示例 |
|---|---|
| `EFFECT_BUNDLE`（2727 行） | `KEY[wh_main_payload_morale_army];DURATION[8];GLOBAL` |
| `TREASURY`（1684） | `AMOUNT[1000]`（负值=扣钱） |
| `TEXT_DISPLAY`（1410） | `LOOKUP[dummy_mission_2_blue_scribes]` |
| `FACTION_POOLED_RESOURCE_TRANSACTION`（943） | `RESOURCE[tmb_canopic_jars];FACTOR[canopic_jars_missions];AMOUNT[50];CONTEXT[absolute]` |
| `CAMPAIGN_PAYLOAD_RECORD`（55） | `PAYLOAD[wh3_main_nor_dilemma_serpent];FACTION;` |
| 无参数 | `WOUND_CHARACTER`、`REBELLION`、`FORM_CONFEDERATION`（`value` 留空） |

**载荷 UI**：`campaign_payload_ui_details_tables`（PK `component`；`icon`、`state`、`sort_order`）——`component` 取**小写**载荷名或 `TEXT_DISPLAY` 的 `dummy_*` 键。`campaign_payload_ui_states_tables`（PK `key`）定义 `state`：`default`/`negative`/`positive`。

> ⚠️ 坑：把 `effect_bundle{bundle_key X;turns T;}` 写进 `payload_key` → 引擎不认；参数一律进 `value` 列，格式 `KEY[...];DURATION[...]`；未注册的 key 静默不发放。
> ⚠️ 坑：`TEXT_DISPLAY` 当真发奖 → **只显示不发放**（UI 写"获得 3 件神器"，背包没有）。实际发放须 Lua 监听任务成功后另发。
> ⚠️ 坑：两难载荷不填 `choice_key` → 该选项无后果；取值来自 `cdir_events_dilemma_choices_tables`（`FIRST`…`NINTH`、`CANCEL`）。任务载荷漏填 `status_key` → 奖励不在完成时发。

### 3.2 选项 / 条件系统

- `cdir_events_options_tables` — 条件/变量白名单 427 条。PK `option_key`：`GEN_*`(210)、`CND_*`(158)、`VAR_*`(57)、`META_OPTION_SET`
- `cdir_events_{dilemma,incident,mission}_option_junctions_tables` — 条件挂到事件/两难/任务。PK `id`。列：`*_key`、`option_key`、`value`、`target`
- `cdir_events_dilemma_choices_tables` / `cdir_events_dilemma_choice_details_tables` — 选项槽位（PK `choice_key`，+`order`）/ 选项音效（PK `choice_key`+`dilemma_key`）

> ⚠️ 坑：把"选项"理解成"两难的多选一" → 该表是**条件/变量系统**；两难按钮由 `cdir_events_dilemma_choices_tables` + `choice_key` 定义。实测样例：`VAR_CHANCE`=100、`CND_FIRST_ROUND`=1、`META_OPTION_SET`=另一条件集 key。

### 3.3 类别 / 发布者 / UI / 特例

- `cdir_events_categories_tables` — 类别白名单。PK `category_key`（`Event`、`Quest`、`Diplomatic`、`Setback`、`Disaster`…）
- `cdir_events_mission_issuer_junctions_tables` — 任务发布者。PK `issuer_key`+`mission_key`（`CLAN_ELDERS`、`PROVINCE`…）
- `prophecy_of_sotek_stages_tables` / `prophecy_of_sotek_stages_to_missions_tables` / `sotek_tooltip_types_tables` — 索泰克预言：阶段（PK `stage`；`effect_bundle`、`order`、`tooltip_type`）/ 阶段↔任务 / 提示类型
- `twad_key_patches_tables` — 声明 key 重命名/映射，不能当删行表。完整键与格式由当前 schema/工具生成，不只按首列判定。

**指定删行：`twad_key_deletes_tables`**。当前本地 schema 收录（v0，`key` 与 `table_name` 为键），RPFM 作者文档明确支持 WH3。原版导出没有此表，只说明该 pack 没有实例，不说明机制不存在。它与 `twad_key_patches_tables` 不同。

怎么做：通过 RPFM 的新 DB / Add Selection to Key Deletes 生成删行记录，复合键交给工具生成；只按当前作者文档或作者环境版本支持的功能操作。不要手猜 `table_name` 的拼法或复合键连接格式。生成后核对所删记录、其他表残余引用、加载组合和游戏内结果；当前 `modcheck` 未完整验证此特殊删行机制，退出 0 不能替代专项核验。此机制来源见 `05` §5；本次没有游戏内重测。

## 4. 仪式域

- `rituals_tables` — 主表。PK `key`。改动：`cast_time`、`category`、`completion_payload`/`start_payload`/`self_payload`、`cooldown_time`、`failure_cooldown_time`、`target`、`required_resources`/`expended_resources`、`influence_cost`
- `ritual_categories_tables` — 类别。PK `id`。列：`trigger_events`、`needs_tracking`、`refund_on_cancel`、`group`、`sort_order`、`ui_icon`
- `ritual_category_groups_tables` — 类别组。PK `key`（+`sort_order`）
- `ritual_chains_tables` — 链。PK `key`。列：`category`、`ritual_sites_required`、`sort_order`、`colour_hex`
- `rituals_to_ritual_chains_tables` — 仪式排入链。PK `order`+`chain`+`ritual`
- `ritual_payloads_tables` — 载荷主表。PK `key`。列：`human_only`、`payload_base`
- `ritual_payload_effect_bundles_tables` — 效果捆绑。PK `payload`+`effect_bundle`（+`duration`）
- `ritual_payload_resource_transactions_tables` — 资源交易。PK `payload`。列：`transaction`、`is_transfer`
- `ritual_payload_spawn_mercenaries_tables` / `_spawn_armies_tables` — 生成佣兵（PK `id`；`spawnable_unit`、`add_mercenaries_to_performing_faction`）/ 生成军队（PK `id`；`spawnable_force`、`spawn_location`）
- `ritual_payload_teleport_armies_tables` — 传送军队。PK `payload`。列：`region`、`vicinity_radius`、`teleport_same_faction_armies_only`、`teleport_only_to_sea`/`_from_sea`、`include_vassal_armies`
- `ritual_payload_add_foreign_slots_tables` / `_change_unit_allowance_capacities_tables` — 加外槽（PK `payload`；`slot_set`）/ 改单位容量上限（PK `payload`；`unit_list`、`capacity`）
- `ritual_performing_characters_tables` / `ritual_performing_character_junctions_tables` — 施放角色（PK `key`；`agent_subtype`、`recovery_time`、`minimum_level`）/ 仪式↔角色（PK `character`+`ritual`）
- `ritual_region_target_criterias_tables` — 区域目标校验。PK `key`。列：`required_subculture`、`own`、`targets_ruins`、`targets_besieged`、`require_walls_present`、`minimum_settlement_level`、`diplomacy_status`、`require_not_at_war`、`permitted_faction_set`
- `ritual_faction_target_criterias_tables` — 派系目标校验。PK `key`。列：`is_human_only`、`permitted_faction_set`、`require_not_at_war`、`allow_vassals_of_humans`

> ⚠️ 坑：往 `ritual_payloads_tables.payload_base` 写效果 → 原版该列基本为空；效果写在 `ritual_payload_effect_bundles_tables` 等子表。

## 5. 池资源域

- `pooled_resources_tables` — 资源。PK `key`。改动：`maximum`/`minimum`、`default_factor`、`ai_ignored`、`income_policy`、`scope`、`appy_income_on_creation`
- `pooled_resource_factors_tables` — 因子。PK `key`（+`is_hidden`）
- `pooled_resource_factor_junctions_tables` — 因子↔资源。PK `unique_id`。列：`factor`、`resource`、`minimum`/`maximum`、`specific_faction_set`
- `resource_costs_tables` — 消耗规则。PK `id`（**字符串**）。列：`treasury_cost`、`expenditure_type`、`income_type`
- `resource_cost_pooled_resource_junctions_tables` — 消耗↔因子绑定。PK `resource_cost`+`pooled_resource_factor`。列：`amount`（负数=消耗）、`context`、`ui_resource_transaction_pooled_resource`
  - ⚠️ **`pooled_resource_factor` 填的是 `pooled_resource_factor_junctions_tables.unique_id`（绑定行 ID），不是 `pooled_resource_factors_tables.key`（因子名）**。原版实测：该列 376 个不同取值 **100% 命中 unique_id**，仅 35 个命中因子名（大量 unique_id 恰好与因子名同名，肉眼查不出来）。填错 → 游戏启动即崩：`The first invalid database record is <cost><factor> in table resource_cost_pooled_resource_junctions_tables`（2026-09-25 `su_xxgxx_vmp` 实测）

**典型链路**：`pooled_resources` 注册资源 → `pooled_resource_factors` 注册因子 → `pooled_resource_factor_junctions` 绑定 → 发放走 `FACTION_POOLED_RESOURCE_TRANSACTION` 载荷（`RESOURCE[...];FACTOR[...];AMOUNT[...];CONTEXT[absolute]`）或 Lua `cm:faction_add_pooled_resource` → 消耗走 `resource_costs` + `resource_cost_pooled_resource_junctions`。

> ⚠️ 坑：新建资源只注册 `pooled_resources_tables` 不绑 factor → 资源永远为 0，加值无效。
> ⚠️ 坑：`resource_costs_tables.id` 不是数字而是**字符串 key**（如 `aislinn_colonies_1`）→ 按数字主键写查不到；`appy_income_on_creation` 原版少一个 `l`。

## 6. 战役组 / 佣兵 / 派系集域

- `campaign_groups_tables` — 组定义。PK `id`（仅一列）。← 所有 `campaign_group_*_tables.campaign_group`
- `campaign_group_members_tables` — 成员。PK `id`。列：`group`、`priority`。← 所有 `campaign_group_member_criteria_*.member`
- `campaign_group_member_criteria_factions_tables` — 派系条件。PK `member`+`context`。列：`context`（`ACTOR`/`OWNER`/`ORIGINATOR`）、`faction`
- `campaign_group_pooled_resources_tables` — 初始资源。PK `campaign_group`+`resource`（+`initial_amount`）
- `campaign_group_pooled_resource_effects_tables` — 池资源效果。PK `campaign_group`。列：`effect_bundle`、`effect_type`、`optional_icon`
- `campaign_group_rituals_tables` / `_ritual_chains_tables` — 解锁仪式/链。PK `campaign_group`+`ritual`/`ritual_chain`。列：`unlock_mission`、`unlock_turn`、`initially_unlocked`

> ⚠️ 坑：一个 `member` 在**同一 `context`** 下绑多个 `faction` → 引擎按 context 只解析一个，其余被忽略（原版 11220 行**零冲突**）。要命中多派系，拆成多个 member key 再注册到同一 group。

**佣兵**：`mercenary_pools_tables`（PK `key`）→ `mercenary_pool_to_groups_junctions_tables`（PK `key`；`group`、`pool`、`initial_unit_count`、`faction_requirement`、`subculture_requirement`）→ `mercenary_unit_groups_tables`（PK `key`；`chance_to_replenish`、`max_count`、`unit_record`）。另：`faction_to_mercenary_set_junctions_tables`（`faction`→`mercenary_set`）、`campaign_mercenary_unit_character_level_restrictions_tables`（`unit`、`character_level`）。

**派系集与 UI**：`faction_sets_tables`（PK `key`）← `ancillaries.faction_set`、`ritual_region_target_criterias.permitted_faction_set`；`faction_set_items_tables`（PK `id`；`culture`/`subculture`/`faction`、`remove`、`set`）；`ui_features_to_factions_tables` / `ui_features_to_cultures_tables` 按派系/文化开关 UI 特性。

## 7. 科技域（表位；做法见 `24-建筑与科技.md`）

科技 UI 按目标种族当前原版结构选择 group 或 tab，具体链见 `24-建筑与科技.md`。

- 事件/池资源/战役组/科技：`incidents`7、`dilemmas`3、`missions`0、`cdir_events_payloads`2、`pooled_resources`2、`campaign_group_members`1、`mercenary_unit_groups`3、`technologies`7

> ⚠️ 坑：游戏更新后照抄旧版本号 → RPFM 导入报"表结构已过时"；以作者环境 `data__.tsv` 第 2 行为准重核。

**验收清单**

- [ ] 表名与列名均来自 `data__.tsv` **第 1 行**，大小写一致（注意 `prioritised`/`prioritized`、`appy_income_on_creation`）。
- [ ] `payload_key` 已在 `cdir_events_payloads_tables` 白名单内；参数写在 `value` 列，格式 `KEY[...];DURATION[...]`。
- [ ] 两难载荷都带 `choice_key`；任务载荷都带 `status_key`。
- [ ] `TEXT_DISPLAY` 型奖励已配 Lua 实际发放，或已确认只需展示。
- [ ] 新池资源已通过 `pooled_resource_factor_junctions_tables` 绑至少一个 factor。
- [ ] 每个 `campaign_group_members` 的 `(member, context)` 只有一个 faction。
- [ ] 建筑效果写在 `building_effects_junction_tables`，`effect_scope` 抄原版同类行。
