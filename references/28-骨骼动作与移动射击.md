# 28 · 骨骼动作与移动射击

> 适用：WH3 的战斗动画接线、借动作、移动射击与异常姿势排查。
> 前置：`12` §6、`23` §4；模型和武器槽见 `27` §1.3–1.5。
> 证据：2026-10-06 su_dgxl 修改记录与解码数据；2026-10-08 用户游戏内反馈。维护者本次未重新进游戏。
> 模型层补充：2026-10-08 对照 scnjwyc `b92d85e` 的诊断方法；§6 为执行与验收约束，没有在作者环境完成模型变形修复。
> 工具登记说明维护：2026-10-14；版本与能力由使用者的环境记录及具体任务实测核实，未新增游戏内验证。

## 1. 把骨骼、动作表、动作文件分开查

| 层 | 查什么 | 不能仅凭什么判断 |
|---|---|---|
| 单位绑定 | `land_units.man_animation`；坐骑和炮械另查相应动画字段 | 看见一个 `.anim` 就以为单位会用它 |
| DB 动画表 | `battle_animations_table_tables.key/skeleton`，使用文化的 `culture_to_battle_animation_tables_tables` 登记 | key 中的 `hu1` 等缩写直接等于 skeleton 或游戏代数 |
| 模型与骨骼 | 模型蒙皮、骨名、挂点、武器槽，与动作骨骼对应 | 同为人形就必然兼容 |
| 动作片段表 | 战斗 `.bin` 的动作槽、候选动作和配置；`.animpack` 可能含同路径片段 | 槽存在就代表姿势、转向与发射时序都正确 |
| 动作和元数据 | `.anim`、动画 `.anm.meta`、声音 `.snd.meta` 及相关资源 | 只改动画路径而忽略事件、混合配置和依赖 |

路径属于 pack 内虚拟路径，沿当前原版和工具解码结果核实。不同骨骼直接借动作可能错位；如果进行了骨骼映射、重定向或重新蒙皮，应作为另一条制作流程验证，不能概括为“跨骨骼永远不能用”。同骨骼也不保证持枪方式、肩肘姿态或武器挂点正确。

`.bin` 与 `.animpack` 不是互相改名的两种后缀。若工程同时提供独立 `.bin` 和 animpack 中同路径片段，检查两份是否一致及实际加载来源。自编二进制时先做无改动的解码→编码往返逐字节核验，再修改；不能把某次工具不能回写的情况说成所有版本都不支持。

## 2. 移动射击不是只加一条属性

依次检查：单位获得移动射击相关属性（此案例为 `mounted_fire_move`）→ 使用的动作表具有对应移动射击槽 → 动作及元数据可加载 → 武器与发射事件吻合。UI 的 `fire_whilst_moving` 标签只负责显示，不能代替行为接线。

以下槽号已在 su_dgxl 及所查原版人形动作片段中对应，其他骨骼/版本须重查槽定义：

| `animation_id` | 所查方向 |
|---|---|
| 1570 | moving_fire_fwd，前进 |
| 1572 | moving_fire_left，向左 |
| 1573 | moving_fire_right，向右 |
| 1574 | moving_fire_bwd，后退 |

动作槽方向与单位最终允许射击的扇形是两个检查项。四槽都有动作不等于获得全向开火；只留前进槽也不能未经实测就当作锁定正前方射界的方法。射界同时查实体、武器、朝向与游戏内表现。

- 移动射击动画是**原地循环**：原版四个方向的 `animroot` 平移恒定，实体的实际位移由引擎按速度驱动；借带根位移的走路动画会造成模型自己在动。
- 优先选同骨骼、同类持械方式且本来用于移动射击的动作。借单手手枪动作给双手长枪时，即使能开火也要检查握持、肩肘和枪口。每次只换一项，以保留能定位问题的对照。

## 3. su_dgxl：从“借站立射击”改成自建走路+瞄准

### 3.1 第一版（2026-10-06，已废弃）

动作表 `hu1_emp_rifle_bayonet` 原有 409 条 entry，补入 1570/1572/1573/1574 后为 413 条；独立 `.bin` 与 `anim_pack_hu1_bayonet_rifle.animpack` 同步修改。四槽都引用**同一**站立射击动作 `hu1_cst_gunnery_rifle_aim_fire_stand_01.anim`，`blend_in_time=0.2`、`weapon_bone=WEAPON_BONE_1`。

**用户实测（2026-10-08）**：不会移动僵化，主要是上半身射击姿势奇怪。由此证明“站立动作进移动射击槽”不必然锁住整个身体，移动、腿部步态、持械姿势要分开验收。

### 3.2 原版机制的正面对照（2026-10-24 解码实证）

| 观察 | 数据 | 结论 |
|---|---|---|
| 四个方向的腿部是否不同 | `hu1_swp_moving_fire_{fwd,left,right,bwd}` 的腿/脚轨道逐帧差 **0.0**，仅 `spine_1/spine_2` 不同（0.02–0.05） | 方向差异只是**躯干朝向**，腿仍是同一套走路 |
| 移动射击有没有根位移 | 四个文件的 `animroot` 平移恒定（如 0.051,0,−0.027） | 移动射击必须是**原地循环**，实体位移由引擎按速度驱动 |
| 走路动画的根位移 | `hu1_sp_walk_01` 的 `animroot` 每 1.1 s 前移 1.373；`hu1_sws_walk_01` 前移 1.659 | 走路带根位移，直接借来当移动射击会让模型自己“走” |
| 移动射击与走路的关系 | 腿部相似、上半身与站定瞄准一致 | 原版就是“走路循环 + 射击上身” |

这些静态观察支持该案例尝试腿部循环与根位移处理；不能据此概括所有骨架的混合机制，真实姿态仍待游戏验证。

### 3.3 该案例的候选做法（非通用生成参数）：用 `anim_format` 生成四个原地“走路+瞄准”动画

历史案例工具链（不随包提供，使用者另核实版本和能力）：`rmv2_anim_blender_import_export` 的 `io_scene_rmv2/anim_format.py` 是不依赖 bpy 的 .anim 读写器，可读 v5–v8、写 v5–v8；用 Blender 自带 `python.exe`（有 numpy）直接 `importlib` 加载即可，无需打开 Blender。读 v8 时注意把模块塞进 `sys.modules` 再 `exec_module`，否则 `@dataclass` 解析报 `NoneType`。

生成参数（39 帧 / 20 fps / 1.9 s，v7，72 骨骼）：

- 下半身：`spear/locomotion/hu1_sp_walk_01.anim` 按时间循环采样（slerp 插值，1.1 s 一周期），`root`/腿/脚/裙/披风的**平移**也取自走路（脚不打滑）。
- 上半身：`rifle/missile_actions/hu1_rifle_aim_fire_{stand,left,right,back}_stand_01.anim` 的 39 帧 1:1 对齐（同时长，事件时间点天然吻合）。`spine_0` 留在下半身（它是腿的兄弟节点，属于髋部），`spine_1` 以上全部取瞄准。
- `animroot` 平移**清零**（对齐原版移动射击）。
- 槽位接 meta 用各方向射击动画自己的 `.meta`/`.anm.meta`（`FIRE_POS`、`EFFECT`、手部姿态与动画同源）；`snd` 用走路脚步声 meta。原版站立射击的 `.snd.meta` 只有 Foley，枪声由武器播，不必也不该在动画里再叠一层。

写入表时先做“解析→重写”逐字节回环（v4/3 的 AnimFragmentBattle：u32 版本、u32 子版本、5 个字符串、2 个 u8、u32 条数、每条 id/blend/weight/weapon_bone/sfv/引用数 + 三条字符串），再改槽；animpack 是 `u32 条数 + 重复: [u16 路径长][路径][u32 内容大小][内容]`（**路径长是 u16**，写错成 u32 会让引擎读出 3.5 GB 的假大小并直接崩溃），与独立 bin 必须同步。

自定义战斗动画表的常规布局：`animations/database/battle/bin/<表名>.bin` + 同目录 `anim_pack_<表名>.animpack`（内嵌同一份 bin），两份都要同步；参考 mod Dreadgunner、su_gmzc 均如此。

### 3.4 验收方法

- 数据层：帧数/时长、四元数模长、无 NaN；下半身与走路逐帧一致、上半身与源射击逐帧一致；`animroot` 平移全 0。
- 视觉层：同一套导入链把 `emp_line_mod.rigid_model_v2` + `humanoid01` 骨架 + 新动画导进 Blender，Workbench 侧视渲染几个关键帧，看“迈步+举枪”是否成立；比只读二进制可靠。
- 工程层：modcheck + 打包后解包回环逐字节比对。
- 容器层：改 `.bin`/`.animpack` 前先对**旧文件**做“解析→重写→逐字节比对”；核对每个长度字段的宽度（u16/u32）和含义（路径长/内容长）。2026-10-24 的崩溃就是 animpack 路径长写成 u32，引擎读出 3.5 GB 假大小、未捕获异常 abort（0xC0000409），进战斗即崩。
- 仍未做：游戏内实测（四方向是否都在迈步时开火、枪口朝向、射击节奏）。静态与渲染通过都不等于游戏内通过。

## 4. 按症状排查

| 现象 | 优先核查 |
|---|---|
| 能走但不射击 | 属性、移动射击槽、武器、目标/射界、弹药与事件 |
| 能走能射，上半身怪 | 持械方式、肩肘姿态、武器挂点、四方向借同一动作、混合参数 |
| 腿僵、滑步或转向跳变 | 运动槽与状态切换、根运动、混合配置；先与不射击移动对照 |
| 全身撕裂或摆大字 | 骨骼/蒙皮不匹配、资源缺失、动作表/文化登记 |
| 枪口方向或发射时机不对 | 武器骨、动画元数据事件、投射物出口与连发配置 |
| 修改无效或影响原版单位 | 实际加载的片段、animpack/独立 bin 一致性、共享动作表和覆盖路径 |

## 5. 验收与记录

- [ ] 静态：骨骼、文化、单位动画键、槽和资源依赖闭合；往返及条目数检查通过。
- [ ] 分别测前进、左右横移、后退、转向；再测站立射击→移动射击→停止→装填→近战切换。
- [ ] 分别观察位移、腿部步态、肩肘与双手握持、枪口方向、弹丸/声音时序，不能用“能开火”替代姿态验收。
- [ ] 单 MOD 对照，确认共用原动作表的单位没有意外变化；多 MOD 再查加载顺序。
- [ ] 记录游戏版本、动作表、槽、候选动作与参数，明确谁进游戏测试及哪些方向尚未验证。

## 6. RMV2 变形：索引、权重与 bind pose 分开诊断

先排除动作键、武器槽、挂点和加载路径，确认运行中真正引用的模型链：VariantMeshDefinition → wsmodel（存在时）→ RMV2。记录源 SHA、RMV2 版本、骨架名、各 LOD/子网格的顶点格式和材质。不可只按“同为人形”或骨索引数字判断兼容；索引到骨名的映射按该格式的骨架/attachment palette 与解析器核实。

| 现象与证据 | 诊断方向 | 应避免 |
|---|---|---|
| 局部指节或关节扭曲，非零权重指向错误骨名或跨骨链 | 骨索引/影响骨错误；用真实动作确认是哪项影响 | 从缺少一个顶点组直接推导整条骨链前移 |
| 骨名正确但交界硬折，同位置 seam 副本在动作中裂开 | 当前拓扑内的权重过渡；同步有依据的副本影响 | 按最近表面从不同体型模型全量转移权重 |
| 权重与动作链正确，大块区域仍持续偏移或拉伸；新旧骨架 rest 矩阵有系统差异 | bind/rest pose 与顶点位置不匹配 | 反复平滑权重、用空间盒硬切顶点而不查根因 |

**【未验证：具体模型的归因与修复】** 这些是上游案例提炼的分流方法，不足以只凭一张截图确诊。工具安装、版本与验证状态由使用者核实；实际修复先确认兼容 RMV2/ANIM 导入器、用户模型和真实动作可用，仅已安装 Blender 不代表完整修复链路已经验证。没有该环境时交付可证明的诊断和待补证据，不能报告已经修好。

### 6.1 候选生成与局部写入

- 保存原始输入，候选写源目录外；输入 SHA 变化时重新取基线，已修复结果不能重复叠加同一补丁。
- 每个 LOD 独立核对拓扑、骨名和位置/权重布局；不能把 LOD0 的顶点号和权重直接复制到其他 LOD。
- 同坐标 UV/材质副本不是可随意删除的重复面。权重平滑按位置与原始权重签名分簇，避免合并本来不同的边界；位置修复核对副本的目标位置与动作分离。
- 直接写二进制时，字段偏移和编码由兼容解析器取得，先证明无改动往返。声明允许修改的顶点/字段/字节；不得套用上游角色的骨索引、阈值、half4 编码调用或坐标变换为通用格式。
- 权重候选保留格式规定及原始量化总和，不产生无权重顶点；最多影响骨数由实际顶点格式确定，不能把 weighted4 的四项规则推广到所有 RMV2。
- 重解析候选并审计 diff：局部补丁只改变声明的字段；版本、LOD/mesh 数、材质、UV、法线、索引及无关数据保持一致。若任务需要完整重导出，另列结构差异，不把其结果假称为逐字节局部修复。

bind 重定向需同名骨映射、适合比较的参考拓扑与一致坐标系。先让理论线性蒙皮结果对齐工具的实际 evaluated mesh，再据此生成候选；不能照抄上游导入器专用的轴变换或单个案例参数。

### 6.2 同一组真实动作验收

原始与候选使用相同动作、帧与视角；按角色实际拥有的动作覆盖待机、移动、攻击、施法、受击、坐骑/战役姿态。看目标区域改善、周边退化、seam 分离、拉伸/塌缩和全模型渲染；不能只用静态 pose、body-only 图或一项畸变指标判断成功。

候选通过静态结构与动作验证后才回填 MOD 源。打包沿用 `03` 的既有授权和现成工具，必要时导出内部 RMV2 比对 SHA；不搬入上游 `pack_map.json` 或默认每次自动写 pack 的流程。游戏内最终验收仍由用户完成，报告未测动作与状态。
